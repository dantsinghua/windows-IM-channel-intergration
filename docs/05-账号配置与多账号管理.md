## 1. 范围与不做

**范围**
- 三通道(企点 / QQ / 微信)的首次启动与首登流程:从资源预检到 `running`,每一步的自动/人工分界、失败分支。
- 凭据保险库(Vault):DPAPI 作用域、条目模型、存放形式、读写接口、审计、"不保存"路径。
- 多账号管理与切换:企点/QQ 的运行集合选择、微信的单槽位切换、掉线检测与重新登录(**不自动重登**,D-2)、设备身份档案库、账号级设置、升级时的保留承诺(A-5)。
- 合规告知页 `P-SETUP` 的内容要点。

**不做**
- 不绕过短信/滑块/扫码/设备确认——凡通道要人证明"是本人",一律停在 `login_required` 等人。
- **不自动重登**(D-2):三通道掉线后系统只置回 `login_required` 并推事件,不用保险库里的账密、不重启容器、不重扫码去「自己登回去」;由人重新发起登录。
- 不做企业微信;不做 frp/tailscale/隧道(基线 §11 第 4 条)。
- 不定义 DDL(归 02)、不定义页面布局(归 01)、不定义安装期状态机(归 03)、不定义资源采样与网络探测(归 04)。
- 不做"设备指纹轮换"、不做跨机迁移登录态(见 §2.5.3 边界)。

### 2.1 企点首次启动与首登

#### 2.1.1 完整流程

**请求边界(R6-78)**:#2 `POST /accounts` 只完成建档,返回 `201 Account(state=created)`;向导保存 `createdId` 后显式 #9 `POST /accounts/{id}/start` 才进入④及后续启动阶段。#9 失败保留该 id,用户重试同账号,不重复建档。下列为完整业务序列,不是一次 #2 请求的执行范围。

```
① 资源预检        GET /resources → can_add.qidian ≥ 1;否则 409 并给替代("可改开 QQ / 停用一个企点")
```

#### 2.1.3 账密的三个来源与"保存到保险库"的语义

| 来源 | 触发 | 密码走向 | 落库 |
|---|---|---|---|
| 向导输入(内存传递) | `P-ACCT-NEW` 表单 | `remember=true`:密码经 #2 写 Vault,显式 #9 后由 Agent 读取;`remember=false`:#2 省略 `secret`,表单提交即清,只在本次首次创建的非响应式局部变量暂留,稳定 `WAIT_PASSWORD` 后经 #12 交给 Agent 内存 | 勾"保存到保险库"才写 Vault;不保存时 #12 受理即清除局部引用,异常清除与 busy 例外见下文 |
| API 传入 | 业务系统 #2 `POST /accounts` 或 #12 `POST /accounts/{id}/login` | #2 只建档,`login.secret` 仅在 `remember=true` 时用于存 Vault,请求结束即弃、不会留给后续 #9;直接本次登录须先 start 再以 #12 `secret` 提交 | `remember` 由调用方给,默认 `false`;不改变 create-only 消费者(R6-78) |
| 保险库读取 | 人发起登录/重启/停用后恢复,或已预授权的启动(§2.0) | Agent → WinAgent `read`(仅 Agent 令牌)→ 内存 | 不再写;掉线不自动重登 |

**R6-78 一次性密码边界**:前端暂留只承接当前用户发起的首次创建动作,必须有有限等待 / 重试预算,不进 Pinia / store、路由、日志、崩溃转储或持久存储,不作自动重登凭据。#12 受理或任何失败、超时、取消、页面卸载立即清除引用;唯一自动重试例外为 #12 明确 `409 NOT_APPLICABLE reason=busy`,仅可在同一次有界流程内重试且不重置预算,其它错误不得自动重试。密码未保留、已清除或过期后走人工输入,不能假完成;`remember=true` 的 Vault 存储失败亦按真实状态提示,不补发缓存密码。

"保存到保险库"勾选 = **三件事同时成立**:①`accounts.login.remember=true`;②`credential_ref="vault://account/qdNN"`;③Vault 有该条目。三者任一不成立即视为"未保存",登录时走 §2.2.7 的人工输入路径。**不勾** = `remember=false`、`credential_ref=""`、Vault 不写;向导明示"下次重登需要你再次输入密码"。

⚠️ 密码错误(⑪c)时**不删** Vault 条目,只标 `suspect`,由人决定改还是删——自动删会把"企点临时风控误报"当成密码错误。

#### 2.1.4 状态迁移(企点)

`created → provisioning(④,#9 显式启动) → starting(④~⑧) → login_required(WAIT_PASSWORD,⑨) → logging_in(⑩) → running(⑪a)`
`logging_in → login_required(⑪b) → [人操作] → running`
`logging_in → error(⑪c BAD_CREDENTIAL)`;`logging_in → login_required(LOGIN_TIMEOUT)`(⑪ 超时:仍在登录阶段,不自动重填,人点「登录」重来)

`starting → error(BOOT_TIMEOUT / APK_UNAVAILABLE / INSTALL_FAILED / NETWORK_UNAVAILABLE)`
`running → degraded`(微信 chatlog 取钥失败 `KEY_FAIL`、锁屏 `SCREEN_LOCKED` 等;登录无关)。🔴 **企点读库不可用 / 拿不到 root 不在此列(R6-32/R6-8,00 §8.1 逐字)**:旁路读库路径变更、schema 变更、`adb root` 失败 ⇒ **`state` 保持 `running`、`capabilities` 一项不减、不进 `degraded`、永不升 `crit`**,只发 warn(**按成因发两种 warn(R6-35)**:拿不到 root → `QIDIAN_NOT_ROOT`;root 正常但读库不可用(库路径/schema 变更)→ `QIDIAN_DB_UNAVAILABLE`;均登记于 02 §3.7)并把读取降级到控件树/截图兜底路(06 §2.9.5)——本册 v0.4.5 曾写的「企点旁路读库失败 → `running → degraded`」**作废**

`login_required` 期间的可做集合按基线 §8.1 新口径(R-06,取代原「只接受 `screenshot/get_state`」):**允许画面注入类** `stream_touch/stream_key/stream_text/stream_scroll` + `screenshot/get_state/login/prompt/login_cancel`,**拒绝一切 IM 写类**(发消息/群操作/`workflow_run` 回 `LOGIN_REQUIRED`)。企点短信/滑块/设备确认正是靠注入类在登录态把码填进画面(旧口径把写类一刀切禁掉会让它们在设计上永远过不去);注入类改的是本机窗口、不产生对外消息,**不过能力总线 GATE**但逐条记审计(`audit_log.kind='stream_input'`,`text` 按 §11.9 [NOBODY] 只记 `sha8+长度`,登录密码不落审计明文)。Agent 每 5 分钟重发一次 `account_state` 提醒事件(同 `trace_id`,控制台去重),**不超时不放弃**——但企点自己的验证页会过期,过期后 Agent 检测到回到登录页 ⇒ `state_code` 改 `LOGIN_TIMEOUT`、`prompt.text="验证已过期,请点「登录」重新发起"`,**不自动重填账密**(D-2:整个验证环节都是登录阶段,由人推进);人点「登录」⇒ `POST /accounts/{id}/login {}` 重走 ⑨⑩(有 Vault 条目则自动填、无则 `WAIT_PASSWORD`)。

#### 2.1.5 S4 手工登录的只读观察与状态同步(R6-80)

- **范围与节拍**:每 **5s** 的只读 job,只处理非 busy 的企点 `login_required` 且码为 `WAIT_PASSWORD`、`WAIT_SMS` 或 `WAIT_CAPTCHA`。`WAIT_DEVICE_CONFIRM`、掉线组、其它通道及邮箱/手机号推断身份不扩入本批。无新增配置键或 REST 端点。
- **设备侧只读**:不填账号密码、不读 Vault、不切换 IME、不点登录、不拉起/强停/重启应用、不自动重登。先核企点确在前台,再核可见主界面结构；uiautomator 不可得时,只允许组合**同一前台 Activity、同一可见树**的严格 dumpsys 结构证据,不得跨 Activity/TabHost 拼接、使用隐藏节点或仅靠某段文本判登录。
- **身份与提交门**:用 Android 兼容的 `find/stat` 读取数据库 UID 候选(主库与 WAL 时间定序仍按 §2.1.1⑪/R6-40),观察 UID 必须与配置的**数字登录身份**严格相等,不猜邮箱/手机号对应 UID。完成观察后再次核账号非 busy、等待状态/登录会话/更新时间没有改变；错 UID、取消、旧会话或并发登录/停止均不提交。
- **提交与降级**:满足上述条件才沿 `logging_in → running` 既有状态序列回填身份并结束本次等待。probe 必须携带 profile 选择事实；仅本次成功提交后才消费 default profile 降级事实,继而保持 `degraded(UI_UNEXPECTED)`，不能因恢复进程/先前 WAIT 分支丢失该事实，也不能把未成功观察的事实残留到后续登录。此类 `degraded` 有有效 UID 时仍允许旁路只读轮询(06 §2.9.5)，不因 UI 定位降级切断收信。
- **可观察性**:真正的读取/探针不可用产生脱敏原因枚举日志或审计,同账号重复失败去重；原始 ADB 输出、异常原文、凭据和正文不记录。正常未到主界面继续安静等待；只有完整身份匹配并成功提交后才记录恢复,不能把普通等待当恢复。取消继续传播，不改账号状态掩盖故障。

### 2.2 凭据保险库(Vault)——放在这里因为企点流程第一个用到

#### 2.2.1 DPAPI 作用域取舍

| 方案 | 谁能解 | 服务账号变更 | 机器迁移 | 结论 |
|---|---|---|---|---|
| A:用户级(`CRYPTPROTECT` 默认,绑 WinAgent 服务账号) | 仅该账号 | 换服务账号 / 重装服务用新账号 ⇒ **全部不可解** | 不可解 | 太脆:LocalSystem→专用账号的迁移就会丢全部凭据 |
| B:机器级 `CRYPTPROTECT_LOCAL_MACHINE` + **附加熵** | 本机任意能读到熵的进程 | 不受影响 | 不可解(机器主密钥不同) | **采用** |
| C:机器级、无熵 | 本机任意进程 | 不受影响 | 不可解 | 太松:同机任何用户态程序调一次 API 就能解 |

**采用 B**:`CryptProtectData(flags=CRYPTPROTECT_LOCAL_MACHINE, pOptionalEntropy=E)`。附加熵 `E` = 32 字节随机数,首装时生成,存 `%ProgramData%\QTrade\winagent\vault\entropy.bin`,ACL **仅 SYSTEM + Administrators 完全控制、其余无权限**(继承关闭)。效果:非管理员用户态程序拿不到 `E` 就解不了;管理员本来就拥有这台机器,不在威胁模型里。**机器迁移不可解是 DPAPI 的性质,不是缺陷**,§2.2.5 明示。

#### 2.2.2 条目模型

`vault://{类别}/{名}`,类别 = 02 `vault_index.scope` 七类(C-06,命名以 02 §3.2/§3.6 为准;`{名}` 即端点里的 `{name}`,含类别前缀):

| 类别 | 名 | 例 | 谁写 | 谁读 |
|---|---|---|---|---|
| `account` | `<account_id>` | `vault://account/qd01` | 控制台向导 / Agent(转写 API 传入) | Agent(登录时) |
| `mail` | `pop3 / imap / smtp`;**`hmac/cmd/<发件方短名>`(每发件人一把)+ `hmac/confirm`(服务端单钥)**(🔴 R6-10 统一,原 `hmac/<短名>` 作废) | `vault://mail/smtp`、**`vault://mail/hmac/cmd/ops`**、**`vault://mail/hmac/confirm`** | 控制台 `P-SET` | Agent(邮件摆渡,06) |
| `api` | `<app_id>` | `vault://api/ops-bot` | Agent(签发 API 客户端密钥时) | Agent(验签) |
| `asr` | `key` | `vault://asr/key` | 控制台 `P-SET` | Agent |
| `winagent` | `agent_token / console_token` | `vault://winagent/console_token` | 安装器 / WinAgent 首装 | 服务侧自身(签发/校验令牌,§2.2.4) |
| `webhook` | `<id>` | `vault://webhook/ops` | 控制台 | Agent |
| `other` | 自由 | — | — | 预留,本册不用 |

值是 UTF-8 字节串(密码/密钥),上限 4 KB;企点条目的值是 JSON `{"account":"…","secret":"…"}`(账号名与密码同封,避免账号名单独明文出现在 Agent 库里)。

#### 2.2.3 存放形式

```
%ProgramData%\QTrade\winagent\vault\
├─ entropy.bin                      32B 附加熵(ACL 收紧)
├─ blobs\<sha256(条目id)>.bin       每条一个 DPAPI blob(文件名不暴露条目名)
└─ (元数据在 winagent.db 的 vault_index 表)
```

`vault_index` 只存条目名与元数据(基线 §7.7 已定),**不存任何可用于还原值的东西**;`blob_sha256` 存的是密文文件的摘要,只用于校验文件未被替换。一条一个文件的理由:单条轮换/删除只动一个文件,不需要重写整库;文件损坏只丢一条。

#### 2.2.4 读写接口 `/wa/v1/vault`(WinAgent **服务**侧 vault 模块,Bearer;令牌分两种作用域)

路径参数 `{name}` = 条目名含类别前缀(`account/qd01`),与 02 §3.6 一致;读动词按 C-06 采本册(读密文是副作用动作:记审计、计 `read_count`,不该是 `GET`)。

| 方法 | 路径 | 作用域 | 说明 |
|---|---|---|---|
| `GET` | `/wa/v1/vault?scope=` | console / agent | 列表:仅元数据(name、版本、updated、last_read、suspect) |
| `HEAD` | `/wa/v1/vault/{name}` | console / agent | 存在性 |
| `PUT` | `/wa/v1/vault/{name}` | console / agent | 写(新建或覆盖,版本+1);body `{value, scope}`;**响应不回显值** |
| `DELETE` | `/wa/v1/vault/{name}` | console / agent | 删(blob 文件先 0 填充再删,元数据保留一行 `deleted_ms`) |
| `POST` | `/wa/v1/vault/{name}/read` | **仅 agent** | 返回明文;console 令牌调用 → 403 |
| `POST` | `/wa/v1/vault/{name}/flag` | agent | 标 `suspect`(登录报密码错) |

- **控制台只能写与删、不能读回明文**:界面上永远显示"已保存(v3,2026-09-18)",没有"显示密码"。理由:一旦控制台能读,渲染进程就成了明文出口,DPAPI 的保护就只剩个形式。
- `read` 只走 loopback(`127.0.0.1:17610`)或 WSL vEthernet 子网(04 的防火墙规则),且请求头带 `X-Trace-Id`,审计行落 `wa_audit_log`。
- 令牌:WinAgent 首装时生成两把,都存 Vault(`vault://winagent/agent_token`、`vault://winagent/console_token`,02 §3.6)。`agent` 令牌是 `secret_ref` 之外的唯一例外——它必须以明文存在 WSL 侧 `/etc/qtrade/winagent.token`(鸡生蛋,C-05),权限 `0600 root`,只能解锁 `/wa/v1`;`console` 令牌**不存 Windows 凭据管理器**(C-04 取代主文档 §4.2):控制台主进程启动时经本地命名管道 `\\.\pipe\qtrade-winagent`(01 §2.3)向 WinAgent **服务**侧取一次,管道服务端校验对端进程后签发,渲染进程永不见 `Authorization`。

#### 2.2.5 轮换 / 删除 / 迁移

- **轮换** = `PUT` 覆盖:版本+1,旧 blob 0 填充后删;Agent 下次登录自然读到新值。企点侧"改密码"必须在企点 App 里改,系统只负责存新值。
- **删除** = 条目 `deleted_ms`,对应账号 `remember=false、credential_ref=""`;下次登录走人工输入。
- **机器迁移不可解**:`P-SET` 保险库区块与导出功能都明示"凭据绑定本机,换机器/重装系统后需重新输入"。系统**不提供导出明文**的功能(没有安全的导出形态);账号列表(不含密码)可以导出。
- **附加熵丢失**(`entropy.bin` 被删)= 全库不可解,等同迁移;WinAgent 启动自检发现熵文件缺失或 ACL 被放宽 → `alert` 事件 + `P-ENV` 红灯。

#### 2.2.6 审计与 Agent 侧处理规则

- `wa_audit_log` 每次 `read/PUT/DELETE/flag` 一行:`ts、actor(令牌 id)、action、target(条目 id)、result、trace_id`;**不记值、不记值的长度、不记摘要**。
- Agent 侧:明文只在登录函数栈内存活;用 `bytearray` 承载,用完 `zero()`;禁止进 `logging`、禁止进异常消息(捕获后重抛脱敏异常)、禁止进事件 payload、禁止进 `commands.args`。代码评审硬规则:任何接触 `secret` 的函数签名带 `SecretBytes` 类型,序列化器对该类型一律输出 `"***"`。
- 读取失败(WinAgent 不可达)⇒ 登录不进行,账号 `error(VAULT_UNAVAILABLE)`,不回退成"让人输入"——那是另一条路径,由人在界面上显式选。

#### 2.3.2 二维码如何安全地展示给控制台

结论:**转发二维码图片,不把 WebUI 暴露给控制台**。
- WebUI(:163NN)有自己的登录口令与全部管理面(改 OneBot 配置、看日志),让控制台直接打开它 = 多一个鉴权体系、多一个可写入口。
- 做法(R6-83)：Agent 仅访问本机 loopback WebUI，以 `/api/auth/login` 鉴权（SHA256(token + `.napcat`)），Credential 仅在内存。`POST /api/QQLogin/GetQQLoginQrcode` 的 `data.qrcode`、`POST /api/QQLogin/RefreshQRcode` 的 `data.qrcodeurl` 均为 URL，不能当 PNG 或跟随下载。真实 PNG 来自 NapCat 写入的固定 `/app/napcat/cache/qrcode.png`；Agent 只读，限 1 MiB，校验 PNG 结构/CRC，不新建二维码副本。首次与刷新均请求新码并等待 PNG 字节变化，避免复用卷内旧码；失败可见，不生成假码。来源：[官方 QQLogin API](https://github.com/NapNeko/NapCatQQ/blob/v4.18.28/packages/napcat-webui-backend/src/api/QQLogin.ts)、[官方二维码写入](https://github.com/NapNeko/NapCatQQ/blob/v4.18.28/packages/napcat-shell/base.ts)。
- WebUI **语义与执行(R6-83)**：登录期启用、运行期关闭，端口始终仅 `127.0.0.1:163NN:6099`；使用 `disableWebUI=false/true` 开/关，运行容器须实际停止/启动并 inspect 确认。临时开默认 10 分钟，`webui_published_until_ms` 只记截止时间，不是开关事实。每秒 `qq_webui_expiry` 只处理已到期、非 busy、无有效登录尝试的 QQ；关闭成功才清截止并记 OK，失败 `503 napcat_webui_unavailable`，保留截止、固定脱敏 warning，下轮重试。配置已关但仍登记截止的失败中间态须强制重启核实生效，不能假称已关。此收尾不发起新登录/新码，原 OneBot 仅做传输重连，H08 按运行期规则处理。
- 二维码只存在当前尝试内存、实时 WS 和 #15 API 响应；Agent 不落 PNG、不进消息/审计，`events_outbox`（WS 规范行与 webhook 副本）和重放均移除 `prompt.qrcode_png_b64`。刷新/重连须经 #15 重取。NapCat 自有缓存/日志是上游行为，不能把 Agent 零副本写成上游也完全不落盘。

**首登 ACCOUNT 的受管收尾(R6-83)**：以实际容器 `Config.Env.ACCOUNT` 判断是否已包含本次确认 UID，不能只信账号记录；已有正确 UID 的普通重启路径也必须核名称/ID。`disableWebUI=true` 在注册 `autoLoginAccount` 回调前返回，不能只写后者就承诺免扫。官方镜像 entrypoint 用 `ACCOUNT` 生成 `-q`；只有本次有效会话已确认 UID、状态为 `logging_in`，并核对登记的容器 ID/名称和专用卷归属时，才允许停止后再次核 ID、移除本账号容器（`volumes=False`）并按原镜像、端口、配额、专用数据/配置卷重建为 `ACCOUNT=确认 UID`。每个异步边界前复核会话；取消/超时/stop/新会话/归属改变均不得继续。保留卷及登录指纹，不操作无关现役容器；新 OneBot 连接复核同 UID 在线后才完成。

**OneBot 配置来源(R6-83)**：初始化官方 `network.websocketServers/httpServers`，内部 3001 WS/3000 HTTP、外部 loopback 映射；默认 `onebot11.json` 供上游创建账号配置，保留其它配置键。先保留/建立 schema 允许的 `napcat.json`，防镜像 entrypoint 首启复制模板覆盖既有接线。

#### 2.3.3 qq_data 免扫的条件与失效处理

免扫命中需同时满足:①`ACCOUNT` 与卷里登录过的 QQ 号一致;②卷里 token 未过期(NTQQ 侧长期离线会过期,经验值 30 天上下,不写死);③未被风控/未在别处以"踢下线"方式登录/未改密码。
失效表现:容器起来后 `get_login_info` 长期 (`qq_quick_login_wait`, 默认 20s) 不返回 user_id,或 NapCat 日志出现需要扫码。处理 = 回到 ⑤b 出码 → `login_required(WAIT_QRCODE)`,**不删卷**(主文档 B.7:删了要重扫并触发风控;卷里的设备指纹要保住,扫码后 token 刷新即可)。
风控形态(扫码后提示"环境异常""需要手机确认")= 人在手机 QQ 上完成,Agent 只等 `get_login_info`;等待期同企点 5 分钟一提醒。

#### 2.4.2 微信槽位与 `account_id` 的结论

**结论:每个微信档案(wxid)一个 `account_id`(`wx01、wx02…`),而不是固定一个 `wx01` 换人用。** 理由:
1. `session_id = {account_id}:{通道原生ID}`、`messages.account_id`——若两个 wxid 共用 `wx01`,两个人的会话与消息会混进同一账号名下,消息库、游标、幂等键全部串号。
2. 基线 §6"`account_id` 分配后永不复用"正是为此:一个 id 永远只指向一个登录实体,切人就换 id。
3. "一机一个在线"用**槽位**表达:`ResourcePool.windows.wechat_slots{used,max=1}`(基线 §7.6 已有),字段 `holder`(当前占槽的 `account_id`)、`pending`(正在登录/切换中的目标 `account_id`,§9 提议 3)、**`pending_expires_at`(R-04,§9 提议 20)**、**`pending_login_session_id`(🔴 R6-6 新增)**。任意时刻微信通道下处于 `starting|login_required|logging_in|running|degraded` 的账号 **≤1**,其余全是 `stopped/disabled`。

**槽位视图字段表(`ResourcePool.windows.wechat_slots`,基线 §7.6;持久化落点 = 02 `resource_pools(pool='windows')`)**

| 字段 | 类型 | 语义 | `pending` 为空时 |

🔴 **空值口径(02 已落)**:两个字符串字段 `pending`、`pending_login_session_id` 在**无 pending 时一律回空串 `""`**(库列 `resource_pools.slot_pending_login_session_id TEXT NOT NULL DEFAULT ''`);**只有 `pending_expires_at` 是 `null`**。消费方(01 元素可见/可点、Agent 判据)一律按**非空串**判,勿写 `!= null`。该字段 **02 已落地**:§3.1 `resource_pools` DDL / §2.2.5 槽位维护 / #69 `GET /resources` 出参 `wechat_slots.pending_login_session_id`。
   - 🔴 **`pending` 必须有 TTL 且失败即释放(R-04,基线 §11.18 [SLOT])**:原口径只写「置 `pending`」没写谁清——一次绑定失败(取钥失败、扫码超时、进程被杀)槽位就**永久卡死、整条微信通道不可用且无恢复路径**。现 `pending` 置位即记 `pending_account_id + pending_expires_at`(默认 `[wechat] slot_pending_ttl_s = 600`,§7),**三条释放路径**:①**失败即释放**——登录/切换流程任一步返回失败或被取消,**同步**把 `pending` 置空(不等 TTL);②**TTL 到期由 reaper 释放**——Agent 每 60s 扫一轮,`now > pending_expires_at` 即置空、推 `account_state` 事件、记审计 `slot_pending_expired`;③**用户手动**——`POST /accounts/{id}/login/cancel` **`{login_session_id}`(R6-6:控制台恒带,取值 = 槽位视图 `pending_login_session_id`;端点侧该参数可选只为 API 兼容)**(§3.2),`P-ACCT` 微信组显示 pending 剩余秒数与「取消绑定」。释放时**同步回收该次绑定的中间产物**:临时 hook / chatlog 进程、未落盘的半截密钥、`accounts/<id>/tmp`(否则下次绑定读到脏状态,与 §2.5.7 停后清缓存同源)。`pending → holder` **只在成功时**转换;`holder` 的释放只走正常 `stopping → stopped`。⚠️ **`holder` 无 TTL,比 `pending` 更需盯**:`pending` 是「正在登录/切换、尚未确立」的临时占位,失败即释放、reaper 兜底;而 `holder` 代表**真实的在线登录态**,**绝不能自动释放**(自动登出会误踢正在用的号)。占 `holder` 的账号若进入 `error` 且长时间不恢复,只**告警**(`alert(error)`)并在 `P-ACCT` 微信组给出**人工**「登出 / 切换」入口(`POST …/logout` 或 §2.4.5 切换),由人决定是否腾槽——系统不自动清 `holder`,也不给它 TTL。
   - 🔴 **holder 故障态的人工接管路径(R4-8 配套 + R5-4,基线 §11.18 [SLOT])**:接管的判据落到**两样具体东西**上(R5-4 补齐):①**时间**——`holder` 账号迁入 `error` 时 `account_runtime.error_since_ms` 记当前 ms(迁出清 NULL,02 §3.1 DDL),「持续超过阈值」= `now − error_since_ms ≥ [wechat] slot_error_takeover_s×1000`(默认 300s,归 02 §7.1 `agent.toml`);②**确认**——切换端点 `#17/#18` 收到 `confirm:true` 才进接管分支。达阈值时 `P-ACCT` 微信组显示故障态(含「已故障 N 分钟」,N 由 `error_since_ms` 推)并出现「强制释放并切换」按钮——⚠️ **R6-4:控制台侧读的是 Account **信封顶层字段** `account.error_since_ms`(基线 §7.1,由 `GET /accounts*` 出参与 `account_state` 事件带出,§3.3;仅 `state=error` 时非空),不读 `account_runtime` 库列;库列只是 Agent 侧的落库形态与判定来源**(01 §2.7.3 微信组、`qt-acct-wechat-holder-force-release`,**未达阈值置灰**);**用户二次确认后前端带 `confirm:true` 重发 `switch`**,Agent 在**一个事务里先把故障 `holder` 停成 `stopped`(令 `slot_holder=''`)再让目标 claim**,并记审计。⚠️ **claim 的 SQL 条件不放宽**——仍是 `WHERE slot_holder=''`(02 §2.2.5 ②),接管靠「先停故障号腾空」而不是改 WHERE 去认 `error` holder;未达阈值 / 不带 `confirm:true` 一律 `409 slot_held_by_error`。⚠️ **仍不自动释放 `holder`**——阈值只是「允许人接管」的前提,不是「到点自动登出」;没有用户确认这一步,`holder` 永远保留(自动登出会误踢正在用的号)。这条与 `pending` 的「失败即释放 / reaper 兜底」是**两套完全不同的语义**,不可混用。
4. `wechat_profiles`(winagent.db)与 `accounts`(agent.db,`channel=wechat`)**一一对应**,`wechat_profiles.account_id` 是 Agent 回写的字符串(02 §2.3 两库不互相引用、无 FK);档案是 WinAgent 侧对同一实体的补充信息(版本、DLL、数据目录)。主从关系与分配顺序见 §2.4.2.1。

**`account_id` 何时分配(🔴 R-23/R-补 重写,取代原「新账号不预分配 id」)**:微信 wxid 要到**取钥成功后**才知道,但 `prompt`/`screenshot`/`stream` 全部是 `/accounts/{id}/…` 形态——**没有 `account_id` 就无处打**。裁决:**新增微信账号时立刻建 `accounts` 行**,之后所有交互都有 `account_id` 可用,**不再把 `login_session_id` 当「无 id 时的替代主键」**(那会让前端与审计出现两套主键)。⚠️ **`login_session_id` 本身保留(基线 N-3)**,但语义收窄为**「一次登录尝试」的标识**——不是 account_id 的替代:进入登录流程时生成、贯穿该次尝试的所有 `prompt`/`account_state` 事件、登录流程结束(成功 / 失败 / 取消)即失效;同一 `account_id` 会连续多次尝试(扫码过期、取钥失败重试、超时重来),前端靠它区分「这条 prompt 属于哪一次尝试」,否则**上一次的过期二维码会覆盖这一次的**;`login_cancel` 也按它定位到具体那次尝试(§2.4.4a / §3.2)。两种入口:
- **"登录已有账号"**:用户在 `P-ACCT` 微信分组里选一个 `stopped` 的 `wxNN` 点"登录" ⇒ 该 id 进 `starting`。
- **"新账号"**:立刻在 `accounts` 分配新 `wxNN`(取未用过的最小 NN,含软删行不复用),落 `state=created`、`self_uid(wxid)=NULL`、`login_mode=qrcode`、`credential_ref=""`,同一事务 `wechat_slots.pending=wxNN` + `pending_expires_at`,并生成本次尝试的 `login_session_id`(格式 `ls_`+ULID,基线 §6/R3-11);`account_state` 事件带**真实 `account_id` + `login_session_id`**(前者标实体、后者标这一次尝试)。扫码 + 取钥成功读到 wxid 后**回填并校验**:
  - ① wxid 是**新号** ⇒ 回填 `self_uid=wxid`,状态序列继续 `provisioning→starting→login_required→logging_in→running`。
  - ② wxid **已有老档案**(用户登了老号,`accounts` 里已有 `self_uid=wxid` 的行) ⇒ **合并到老档案**:刚建的临时 `wxNN` 行标 `merged_into=<老 id>` 并软删(`deleted_ms`,`account_id` 永不复用),槽位 `holder`/`pending` 归**老档案**的 id,后续 `running` 挂在老 id 上;弹提示「这是已存在的 wx02,已按 wx02 登录」。
- 选了 `wx02` 登录、却扫出来是另一个 wxid:`wx02` 回 `stopped(state_reason="扫码登录的是另一个微信")`,扫到的 wxid 按上面 ①② 处理——**微信已经登进去了,不能因为选错而登出它**,只做归属修正并弹提示。

##### 2.4.2.1 `wechat_profiles` 与 `accounts` 的主从、id 分配顺序与失败回滚(G-18)

🔴 **R6-58 (cl):合并(登了老号 ⇒ 新建的临时 `wxNN` 软删并入老档案)时,**不为被软删的那个临时 id 发 `account_state` 事件**。** 判据:合并整个走库(一个事务:新行 `merged_into=老id`/`deleted_ms=now`,槽位 `holder=老id`)并留一条审计 `account.wechat_merge`;**对外只发老 id 的 `running` 事件**。理由:那个临时 id 从来没有真正「运行」过,给它补发一串状态事件会让控制台的账号列表先冒出一行再抹掉,时间线里还多一个不存在的账号。控制台要把临时行从列表里去掉,靠的是 **`#18` 响应里的 `{merged_into: 老id}`**(它是发起方,自己知道该抹哪一行),不靠事件。


**谁是主**:`accounts`(agent.db)是**主**——`account_id` 由 Agent 分配(基线 §6),`wechat_profiles`(winagent.db)是 Windows 侧对同一实体的**从属补充**(版本、DLL、数据目录、仪式记档),`wechat_profiles.account_id` 是 Agent 回写的字符串(02 §2.3:两库不互相引用、无外键)。**两表一一对应的判据是 `wxid`**:`accounts.self_uid = wxid`(§3.1),`wechat_profiles.wxid` 为主键;`wechat_profiles.account_id` 允许短暂为临时 `wxNN`(命中老档案时下面第 4 步会改指老 id)或短暂为 NULL(第 1 步写入前),但**任何 `running` 的微信账号两边必须都已填且为最终 id**。

**分配顺序(🔴 R-23 重写:`account_id` 在扫码前就已建,取钥后回填 wxid;🔴 R2-2 再校:取钥三段先做完、两钥同轮落盘后才 `bind`,不先 `bind` 再试钥;全部由 Agent 驱动,WinAgent 从不回调)**:

```
0) 新增微信账号 ⇒ Agent 事务内先分配 wxNN:state=created、self_uid(wxid)=NULL、login_mode=qrcode、credential_ref=""

   —— 此后 prompt/screenshot/stream 全用 /accounts/wxNN/…,没有「无 id」窗口

      wechat_slots.holder/pending 改指老 id，running 挂老 id;提示「已按 <老 id> 登录」

```

| 第 2 步 取钥失败(只拿到一把 / 全 DLL 失败) | `degraded(KEY_FAIL)`,读写都拒(§2.4.7);🔴 **R6-58 (cj):`KEY_FAIL` 与 `SCREEN_LOCKED` 同时成立时取 `KEY_FAIL`** —— 两者都会让账号进 `degraded`,但 `KEY_FAIL`(读写都拒)**严格包含** `SCREEN_LOCKED`(只拒写);取更严的那个,界面上给出的引导(「重试取钥 / 按随包版本重装微信」)才对得上真正的阻塞点。|**失败即同步释放 `pending`** + 回收中间产物,**不进 bind**;人可重试取钥(`POST /wa/v1/wechat/key/retry`)或按随包版本重装微信 |

| 第 4 步 `bind` 网络失败/503 | `accounts` 行留 `created`(不 stopped、不删);Agent 每 5s 重试 `bind`(幂等),超 `bind_retry_max`(默认 12 次)⇒ `error(VAULT_UNAVAILABLE)` 同款环境类错误、**失败即同步释放 `pending`**、`alert`;人可在 `P-ACCT-DETAIL`「立即重试」 |
| 第 4 步 `bind` 返回 409(该 wxid 已绑别的 `account_id`) | 与第 3 步 b) 合并逻辑同路:以 **winagent.db 已有的 `account_id` 为准**,把刚分配的 `wxNN` 行标 `merged_into=<老 id>`+`deleted_ms`(软删、永不复用),改用 409 里带回的 id;若 `accounts` 无此 id 则按该 id **重建**一行(`state=created`,`self_uid=wxid`),这是两库唯一一处「从表反向修主表」,并写 `audit_log` |
| 第 5 步之前 Agent 崩溃/重启 | 启动自检:`accounts` 中 `channel=wechat AND state IN (created,provisioning,starting,logging_in)` 的行 ⇒ 调 `GET /wa/v1/wechat/status`:微信仍登录且 wxid 相同 ⇒ 续走 2)~5)(取钥→回填→bind);不同或未登录 ⇒ 该行 `stopped(state_reason="登录过程中断")`,槽位清空 |
| 会话代理崩溃(微信仍在) | 会话代理重启后重读 `xwechat_files` 目录名恢复 wxid,`wechat_profiles` 是持久表不丢;Agent 侧 `GET /wa/v1/wechat/status` 恢复 ⇒ 按上一行续走 |

**断连期间的规则**:Agent 不可达时会话代理**不回填 `accounts`、不合并档案**(它没有这个权力),只把 `identified` 状态挂在 `login/status` 上等 Agent 来拉;`wechat_profiles` 可以先有 `wxid` 行(那是 Windows 侧事实)。反向:会话代理不可达时 Agent 已建的 `wxNN` 行停在 `starting`,超 `qr_max_wait_s` 转 `stopped`、释放 `pending`。

#### 2.4.3 讲述人仪式

判据分两层:**目标是"UI 树可见"**,讲述人只是手段。

  4. 状态 `login_required(WAIT_NARRATOR)`,`prompt` 带倒计时(`narrator_min_seconds` 默认 300):自讲述人启动起满 5 分钟且微信已登录 ⇒ 关闭讲述人(`taskkill Narrator.exe`)⇒ 重新 `ui_tree_visible()`;仍不可见 ⇒ `degraded(WAIT_UI_TREE)`,提示"再做一次仪式"(上限 `narrator_max_rounds`=2,超出 → §10 待定 1 人工判断)。

#### 2.4.4a 🔴 取钥的正确时序(2026-09-18 实测,验证报告附录 C.3/C.4b)

**实测结论(微信 4.1.12.26 + wx_key2.dll,已复现)**:两把密钥来源不同、触发条件不同,且 **chatlog 要求同一次运行内都拿到才落盘**——只拿到 `data_key` 会打 `WRN 30秒轮询结束，已获取数据库密钥，但未获取到图片密钥` 并**整轮作废**(实测 14:55 那轮如此,事后 `chatlog.json` 里 `data_key` 仍为空)。

| 密钥 | 取法 | 触发条件 | 窗口(单次运行) |
|---|---|---|---|
| `data_key`(解消息库) | wx_key.dll **远程 hook** | **微信「登录」那一刻**;⚠️ 已登录状态下装 hook 永远等不到;**快捷登录(免扫码)同样有效** | **前 30 秒** |
| `img_key`(解 `.dat` 图) | 原生**内存扫描** | 微信进程内存出现该密钥,即**打开过任意图片** | 约 **60 秒**(并行扫描) |

**正确流程(会话代理执行,`P-ACCT-NEW` 微信分支按此引导)**:

```
a) 起 hook       会话代理跑 chatlog.exe key(按档案 last_wxkey_dll 或 03 矩阵候选序选 DLL)
                 debug 日志出现「检测到的微信版本 X / 目标函数地址 0x… / Hook安装成功」= DLL 与该版本适配 ✅
                 ⚠️ 这三行只证明"hook 装上了",不证明"取到密钥"——别把它当成功
b) 触发 img_key   state=login_required(WAIT_KEY_IMG),引导「请在微信里打开任意一张图片」
c) 触发 data_key  state=login_required(WAIT_KEY_RELOGIN),引导「请退出微信登录并立刻重新登录(快捷登录即可,无需扫码)」
                 ⚠️ 必须在该轮**前 30 秒**内完成;超时则本轮作废,回 a 重装 hook 再来(**循环重试**,见下)
d) 落盘判据      ~/.chatlog/chatlog.json 的 history[0].data_key 与 img_key **同时非空**;
                 只看 stdout 的「获取到数据库密钥」不够——那一轮可能仍因 img_key 落空而不落盘
```

**两个场景的差别**:
- **首登(微信本未登录)**:③ 拉起微信前先做 a);用户扫码可能**超过 30 秒窗口**(要掏手机),所以 a)~c) 必须做成**循环重装 hook**(实测脚本连跑 8 轮 ×100s,第 2 轮命中),不能一次失败就判 `KEY_FAIL`;扫码登录成功后再引导 b) 点图片,若该轮 `img_key` 落空则整体重来一轮(此时微信已登录,c) 改为"退出重登")。
- **已登录(补取钥/换 DLL 后重取)**:直接 a) → b) → c),c) 用退出重登触发。

**取钥失败的排查顺序(🔴 v0.3.1 调整,原来第一项是换 DLL)**:
1. **是不是没有重新登录**(最常见;hook 日志有"Hook安装成功"却无"获取到数据库密钥"⇒ 就是它);
2. `img_key` 是否同轮落空(日志有"已获取数据库密钥，但未获取到图片密钥"⇒ 引导点图片后整轮重来);
3. 微信版本与 DLL 不适配(日志**没有**"目标函数地址"或报"模式匹配失败,找到 0 个结果"⇒ 换 `wx_keyN.dll` 重试,顺序 §7);
4. 微信未登录/停在登录页、会话代理不在线、chatlog 被杀。

**`state_code`(§2.0 等人组,基线 §8.1 已正式补登两码)**:`WAIT_KEY_IMG`(等用户打开任意图片取 `img_key`,窗口约 60s)、`WAIT_KEY_RELOGIN`(等用户退出微信重新登录取 `data_key`,窗口约 30s)。🔴 **两个独立码、不许合成**:两者给用户的指示完全不同(打开图片 vs 退出重登),合并成一个「等取钥」会让界面说不清此刻该干哪件、而**顺序做反(先重登再点图 / 未先装 hook)整轮作废**。两者都伴随 `login_required`,`prompt.text` 给具体动作与剩余秒数(60s/30s 倒计时),`P-ACCT-NEW` 与 `P-ACCT-DETAIL` 按码渲染引导卡片(01 §4 元素待补)。

**证据**:`design/验证-微信静默安装卸载-20260918.md` 附录 C.3(触发条件与日志原文)、C.4b(15:00:35 那轮两把齐、端到端 decrypt success + HTTP 200 读出 2162 会话/66 群)。

#### 2.4.5 切换(登出当前 → 登入另一个)

两个端点(C-13/C-42):切到已有档案 `POST /accounts/{wxNN}/switch`;登新号 `POST /accounts/switch {target:"new"}`。均为 Agent 侧入口,内部调 WinAgent(服务转会话代理):
```
1) 排空:holder(如 wx01)进入 stopping —— 拒绝新的写指令(返回 NOT_READY,error.message="微信正在切换账号"),
   队列里已受理的写指令等它跑完(上限 switch_drain_timeout=60s,超时的按 TIMEOUT 回执);
   正在跑的工作流:当前步跑完后挂起(run 状态 paused,reason=account_switching),不自动续跑
2) 🔴 **R6-58 (ch):这一步的两半各由谁做,逐字定死** —— ①**会话代理侧**「先停 chatlog 再关微信」**内含在 `#34 POST /wa/v1/wechat/logout` 里**(Agent 只调这一个端点,不另发「停 chatlog」的指令;顺序由会话代理保证,因为 chatlog 的 DLL 注在 `Weixin.exe` 里、反过来做会把注入残留在一个正在退出的进程上);②**Agent 侧**停 `wechat/read` 拉取**不需要专门的动作** —— 账号状态一旦离开 `running`,轮询循环自然不再轮到它(`WechatAdapter.stop` 只负责清进程内的内存态)。**别把 ① 拆成两次调用**,也别在 Agent 侧另加一个「暂停拉取」的开关(两个开关必然有一个忘了关)
3) 登出微信:§2.4.6
4) holder → stopped(state_reason="已切换到 wx02");wechat_slots.holder="",pending=目标
5) 目标按 §2.4.4 ③~⑦ 走;新 wxid 走 §2.4.2 的分配;pending 清空、holder=新账号
6) 挂起的工作流留在 paused,由人决定续跑(它绑定的是 wx01,现在 wx01 已 stopped,续跑必失败,不做自动迁移到 wx02)
```
切换期间任意一步失败(微信没起来 / 扫码超时 30 分钟)⇒ 槽位空、目标回 `stopped`,`alert` 事件;**不会自动把 wx01 登回去**(那需要人再扫一次码,自动做没有意义)。

#### 2.4.6 登出方式的结论

**结论(P-31 默认定案 → 安琳 D-1 拍板**定案**):微信登出 = 结束进程(先 `WM_CLOSE` 优雅关闭,10s 未退再 `taskkill /F`),UI「退出登录」按钮仅作可选模式。** 理由:
- 微信 PC 无论用哪种方式退出,下次换号都要扫码(基线 §8.4),两种方式在"下次登录成本"上**无差别**。
- pyweixin 的「退出登录」(`Uielements.LogoutButton`)依赖 UI 树可见与窗口前台,而切换时恰恰可能处于 `degraded(WAIT_UI_TREE)`——用最脆的路径去做最需要确定性的事不合理。
- 结束进程的风险:①微信正在写库——微信本地库是 SQLite WAL,进程终止不会损坏,最坏丢最后一次未 checkpoint 的写(消息在服务端,重登会拉回);②chatlog 已注入 Hook 的进程被杀——先停 chatlog(§2.4.5 第 2 步)即避免;③UI 登出会让微信在服务端记"主动退出",进程终止记"离线",目前没有证据表明后者触发风控;若现场出现相关风控再切 `ui` 模式(配置项,无需改码)。
- 配置 `[wechat] logout_mode = "process" | "ui"`;`ui` 模式失败自动回落 `process`。

#### 2.4.7 取钥失败 ⇒ `degraded` 的能力结论

**结论:`degraded(KEY_FAIL)` 下读与写都不开放,只剩 `get_state / screenshot / list_sessions(pyweixin 走 UI,可选)`。**
- 读:chatlog 拿不到 Data Key,解密库读不了 ⇒ `read_messages` 不可用,这是直接的。
- 写:pyweixin 本身仍能点发送,但微信发送确认**只有** chatlog 读回这一种手段,且微信没有 `confirm=false`、10s 读不到即 `SEND_FAILED`(主文档 C.4.2/C.4.4)⇒ 没有 chatlog 的写 = 每一条都判失败还可能已经发出去了,上层按幂等键重试又发不出去确认——**这是最危险的形态(发了却报失败)**。故写类指令在 `degraded(KEY_FAIL)` 下直接拒 `NOT_READY`(`error.message="微信解密不可用,无法确认送达,已拒绝发送"`)。
- 恢复路径:03 补新 DLL(升级包)→ Agent 调 `POST /wa/v1/wechat/key/retry` 由会话代理重试试钥 → 成功即 `running`;或引导用随包版本重装微信(§2.4.1)。

```mermaid
    W-->>A: {phase:key_failed} → Agent 置 degraded(KEY_FAIL);失败即释放 pending,不 bind
  end
  W->>W: 满 5 分钟且已登录 → 关讲述人 → 复测 ui_tree_visible()
```
(图中 W→A 的箭头都是 Agent 轮询 `login/status` 的**响应**,不是回调。)

**"切换"在企点/QQ 的含义** = 选择哪些账号处于运行集合。`P-ACCT` 提供"运行集合"视图:勾选目标集合 → 系统算差集 → 先 stop 多出来的、再按序 start 缺的;资源不足 ⇒ 整个提交拒绝(409)并给建议("再停一个企点即可"),**不做部分执行**(部分执行会让人搞不清哪些成功)。
**开机自恢复(C-44,判据采 02 §2.6)**:Agent 启动(WSL 重启后)对 `accounts where enabled=1 AND auto_recover=1 AND deleted_ms IS NULL AND account_runtime.desired_state='running'` 按 `accounts.seq` 升序逐个 `start`(全局串行)。`desired_state` 是「用户想让它跑」(start/stop 改它),与实际 `state` 分离——按它恢复才不会漏掉「用户点了启动、还没起来就断电」的账号(本册 v0.1 的 `last_state IN (running, degraded)` 判据作废,`accounts.last_state` 列随之不再需要)。`auto_recover`(§2.5.5)是 `accounts` 列:`enabled=false` 是停用,`auto_recover=false` 是「启用但不自动拉起」——两者都为真才进恢复集合。`remember=false` 的企点见 §2.2.7 只起容器不登录;微信账号只恢复 `holder`(槽位 ≤1);任一账号启动失败不阻塞后面的,失败的记 `error` 与 `alert`。🔴 **自恢复拉起的企点同样走 §2.1.1 ⑤b `ensure_root`(R6-18/R6-28)**:WSL/容器重启后 adbd 一律回落非 root,漏了这步账号会「起来了、能发消息、就是读不到消息」;恢复用 `adb disconnect/connect 127.0.0.1:160NN` 只动本账号,**绝不 `kill-server`**(否则把已恢复好的兄弟账号一并打 `offline`,04 §2.7.4 第 3 条)。自恢复过程中 `P-DASH` 显示"正在恢复 2/3"。**`auto_recover` 的前提是用户已登录 Windows(安琳 A-7 拍板接受)**:用户会话代理随用户登录才起,**用户未登录 Windows 桌面时 WSL/Agent 不会自动起来,账号不自动恢复**——这是拍板接受的行为,不是待定代价;自恢复从用户登录桌面后开始(告知页 §6.1 写明),不做「自动登录桌面」之类的运维绕法。⚠️ 自恢复是「启动」不是「重登」:它对 `stopped` 的账号做 `start`,企点凭 `/data` 登录态或 Vault 账密进入(人预先授权,§2.0);运行期掉线的账号处于 `login_required`、`desired_state` 仍是 `running`,但自恢复**不会**替它重登——它只在 Agent/WSL 重启时对不在线的容器做 `start`,起来后企点若落在登录页仍停 `login_required` 等人(D-2)。
**批量操作边界**:`POST /accounts/batch {ids:[…], action}` 必须显式列 id,不接受 `"*"`(主文档 A.6 广播同规);批量内部仍串行;任一失败不回滚其它(启停本来就是幂等的)。

**内存压力下的账号处置(E-19,基线 §11.12 [MONITOR];判据与算法在 02 §2.2.5,本册定人机分界)**:资源池预检管的是「**新增/启动前**够不够」,而运行期实占 ≠ 预算,故 02 的 `monitor` 还会盯整机可用内存(`[pool] mem_warn_mb / mem_critical_mb`,与 §11.11 [DISK] 磁盘水位**独立计算、各自触发**)。低于水位时系统的动作分层,**核心口径是「只建议、不自动停用户的账号」**:
- `warn` ⇒ `alert(MEM_PRESSURE, warn)`,控制台显红,不停任何账号。
- `critical` ⇒ ①**暂停新增与自动恢复**——`POST /accounts` 与开机自恢复一律 `409 RESOURCE_EXHAUSTED`(`error.reason='mem_pressure'`);②给出一份 **LRU 建议停用名单**,放进 `error.alternatives` 与 `MEM_PRESSURE` 事件的 `evidence.lru_suggest[]`——名单按各账号**最近一次收发消息时间**升序,**最久没收发的排最前**(取 `messages.received_ms` / 发送 `confirmed_ms` 的较晚者),**由人在控制台点「停用」才真正停**,系统只提示不代劳。
- **唯一自动停的例外**:账号 `settings_json.auto_stop_on_pressure=true`(默认 **false**,§2.5.5);开了的账号才允许被系统按 LRU 顺序逐个 `stop` 直到回到 `mem_warn_mb` 以上,每次 `stop` 记审计。默认关意味着**用户的账号不会被系统擅自停掉**。
- ⚠️ **这与「资源不足拒绝新增」是两件事**:后者是新增/启动前的预算门(`409 RESOURCE_EXHAUSTED`,§2.0 资源预检),发生在账号起来**之前**、不碰任何在跑的账号;本条是运行期实占超水位,针对**已经在跑**的账号,而且默认只出建议名单。单容器超自身 `--memory` 由 cgroup 兜底(`CONTAINER_OOM_KILLED` 告警 + §5 上限内自动重启),与整机水位是两层。名单与实占数呈现在 `P-RES`(§4)。

#### 2.5.4 掉线检测与重新登录(三通道;D-2:一律不自动重登)

**原则(安琳 D-2,基线 §11.15 [LOGINPHASE])**:掉线 ⇒ 系统只做三件事——①置 `state=login_required`、`state_code=掉线原因`(`KICKED / LOGGED_OUT / TOKEN_EXPIRED / LOGIN_TIMEOUT`);②推 `account_state` 事件(`prompt` 引导「请点『登录』重新登录」);③`alert(warn)` 一条。**不用保险库账密自动填、不重启容器去快速登录、不自动重扫码**——三通道无例外,企点也不。人重新发起登录后走各通道的**登录阶段**(§2.1.1 ⑨ 起 / §2.3.1 ⑤ 起 / §2.4.4 ③ 起),其中的短信/滑块/二维码/设备确认都是登录阶段的一部分(`WAIT_*`),不算故障。

| 通道 | 检测手段 | 掉线后系统动作 | 人如何重新登录 |
|---|---|---|---|
| 企点 | ①`get_state` 巡检(默认 30s)返回 `LOGGED_OUT`;②指令回 `LOGIN_REQUIRED`;③控件树(拿不到则截图离线 OCR)出现登录页 / "在其他设备登录"弹窗 | `login_required(LOGGED_OUT)`;被顶下线 ⇒ `login_required(KICKED)`;容器与 `/data` 原样保留,**不自动重走 ⑨⑩** | `P-ACCT-DETAIL` 点「登录」⇒ `POST /accounts/{id}/login {}`:Vault 有条目则自动填(人发起)、无则 `WAIT_PASSWORD`;之后按 §2.1.1 ⑩⑪ |
| QQ | ①OneBot WS 断连——Agent **重连 WS**(传输层,不是登录)`qq_reconnect_grace`(60s)内仍连不上;②`get_login_info` 无 user_id;③NapCat 推 `meta_event.lifecycle` 非 connect / 日志出现需扫码 | `login_required(TOKEN_EXPIRED)`(token 失效)或 `login_required(KICKED)`(被手机端下线);容器**保持运行、不自动重启**、不自动出码;容器自身退出是 `error(CONTAINER_EXIT)`,归 §5 不归本表 | 点「登录」⇒ Agent 重启容器(`ACCOUNT` 快速登录,`qq_data` 不删)⇒ 免扫命中即 `running`,否则出码 `WAIT_QRCODE`(§2.3.1 ⑤b) |
| 微信 | ①主窗口消失 / 出现登录窗口;②`Weixin.exe` 进程退出;③会话代理报 chatlog `/health` 失败且微信不在线 | `login_required(LOGGED_OUT)`;槽位 `holder` 保持为它(它仍是「该在线的那个」),不自动拉起微信、不自动登回 | 点「登录」⇒ `POST /accounts/{wxNN}/switch`(目标就是自己,排空步骤天然为空)⇒ §2.4.4 ③ 起,人扫码 |
| 微信(chatlog 挂、微信在线) | Agent `wechat/read` 连续 3 次异常或会话代理报 chatlog `/health` 失败,而主窗口仍在 | **不是掉线**:`degraded(KEY_FAIL)`,会话代理自动重启 chatlog + 试钥(`key_retry_per_hour=3`)——这是修我们自己的进程,不是重登微信 | 无需人;超限停在 `degraded` 并 `alert(error)`,人可 `POST /wa/v1/wechat/key/retry` |
| 微信(锁屏,C-20) | 会话代理 `WTSRegisterSessionNotification` 收到 `WTS_SESSION_LOCK`,或 `OpenInputDesktop` 失败 | **不是掉线**:`degraded(SCREEN_LOCKED, state_reason="Windows 已锁屏,发送不可用")`:**读取正常**(chatlog 不依赖桌面,Agent 照常拉 `wechat/read`),**写类指令拒 `NOT_READY`**(pywinauto 拿不到前台窗口;与 `KEY_FAIL` 的「读写都拒」不同);工作流当前步等待而非失败(受 `timeout_ms`);`P-ACCT` 该行标「已锁屏」 | 人解锁 ⇒ `WTS_SESSION_UNLOCK` 后自动回 `running`,不需要扫码(这不是登录) |

**事件与告警口径**:每次状态迁移一条 `account_state`;掉线那一刻 `alert(warn)` 一条(码名 **`ACCOUNT_OFFLINE`**,登记 02 §3.7,`subject=account:<id>`、`evidence{code, offline_count_1h, last_offline_at}`;同一账号 1 小时内第 3 次掉线升级——**「升 `error`」= 告警 `severity` 升 `crit`(00 §7.5 告警只有 info/warn/crit 三级),不改账号 `state`**;R6-56——计的是**掉线**,不是登录阶段里的验证环节;`offline_count_1h` 按 `account_runtime.last_offline_ms` 滚动 1 小时);`login_required` 期间 Agent 每 `login_remind_interval_s`(300)重发一条同 `trace_id` 的提醒事件(控制台去重),**不计入告警**、04 健康项不把它当异常。
**不再有的东西(v0.3 删除)**:重登限流令牌桶、`relogin_*`/`relogin_backoff_s` 配置、`account_runtime.login_attempts_json`、`RATE_LIMITED` 码、`P-ACCT-DETAIL`「立即重试(限流放行)」按钮——没有自动重登就没有限流。`POST /accounts/{id}/login` 现在只有一个含义:**人发起登录**。
**为什么企点也不自动重登**(不重论,只记理由供后来者):被顶下线的互踢循环、验证页过期后反复重填触发风控、以及「自动重登 + 限流 + 退避」这套机制本身就是最大的复杂度来源;交易员本来就在盯控制台,点一下「登录」的成本远低于一次封号。

#### 2.5.7 容器停止即清缓存(E-19,基线 §11.12 [MONITOR])

**结论:账号一旦落 `stopped`,收尾步同步清掉「可再生的临时数据」,绝不动登录态与业务数据。** 本册是账号生命周期的出处,故在此定**在状态机哪一步做、清什么/不清什么、四条路径如何覆盖**;**具体清理实现(命令、目录、幂等)归 02 §2.2.4 `runtime` 的 `_purge_ephemeral(acct)`,本册不重复列命令**。

**在状态机的哪一步做**:清理挂在 `stopping → stopped` 的**收尾**——容器已 `stop`、账号已置 `stopped`**之后、释放资源池额度之前**同步做完(02 §2.2.4:落 `stopped` 之后、释放额度之前调 `_purge_ephemeral`)。所有把账号带到 `stopped` 的入口都经这一步:§2.5.2 的**停止**、**重启**(stop 段)、**停用**(先 stop),以及 §2.4.5 微信**切换**里 holder 的 `stopping → stopped`。清理是停止流程的一部分,不是独立作业。

**清什么 vs 绝不动(分界即「停止」与「purge」的分界)**:

| 类别 | ✅ 停止即清(可再生临时数据) | 🚫 绝不动(登录态 / 业务数据) |
|---|---|---|
| 容器内 | `/data/local/tmp/*`(截图、`uiautomator dump` 落点、frida gadget 临时);frida 注入的临时脚本 `/data/local/tmp/*.js` | `/data` 卷(企点 `wtlogin_guid/qimei36` 等登录态、App 数据) |
| 宿主·账号目录 | `accounts/<id>/tmp/`(截图 / dump 暂存)整目录 | `accounts/<id>/data/`(含 QQ `qq_data`、napcat_config)、`device_profiles`/`profile.json`(设备身份) |
| 宿主·媒体 | `media/tmp/` 中**属于该账号**的下载中间文件(按下载任务 `account_id` 前缀/owner 记号筛,不误删别账号在途下载) | 已入库媒体 `media/<yyyymm>/`(去重共享,`purge` 才按 refcount 处理) |
| 推流 / 转发 | scrcpy-server 推流临时文件;`adb forward --remove tcp:166NN`(frida 转发)残留;napcat WebUI 临时 | 消息库 `messages`/`messages_fts`、审计、游标 |
| 微信通道对应物 | chatlog 临时文件、pyweixin 截图缓存(UI 自动化产物) | 微信登录态与 `xwechat_files`(用户聊天数据,`purge` 都不碰,P-33);`wechat_profiles` 档案 |

**四条路径**(都落到同一收尾步,差别只在何时触发):

| 路径 | 触发点 | 清理时机 |
|---|---|---|
| 正常停止 / 停用 | `POST …/stop`、`disable`、微信切换 holder 停 | `stopping → stopped` 收尾同步清完,再释放额度 |
| 重启 | `POST …/restart` | stop 段落 `stopped` 时清一次(与正常停止同一步);start 段照常拉起 |
| 崩溃 / 断电(没走到收尾) | 容器意外退出、Agent/WSL 崩溃重启 | **下次启动前预清理补做**——`start(acct)` 在 `provision/inspect` 之前先跑一次 `_purge_ephemeral`,把上次没干净的脏临时清掉(容器已不在则容器内那步跳过、只清宿主侧);保证脏临时不累积、也不被误当有效数据 |
| 升级 / 关机 | 镜像升级重建容器、整机关机后再开 | 升级复用同卷(§2.5.6 登录态保留),重建前的 stop 走正常收尾;关机后再开走崩溃路径的启动前预清理 |

**审计**:每次清理记一行 `audit_log(op='runtime.purge_ephemeral', detail_json={account_id, freed_mb, targets:[…]})`,`freed_mb` 也进 `P-RES` 的「上次清理清出 MB」(§4)。**幂等**:全部「存在即删、不存在跳过」,可重复调用不报错。⚠️ 本条只清临时;停用/删除账号对**数据卷**的处理另按基线 §11.7 [KEEPVOL] 与 §2.5.2(软删保留、`purge` 才真删),两者互不冲突。

### 3.3 事件 payload(提议,基线 §7.5 `account_state`)
```jsonc
{ "event":"account_state", "account_id":"qd01", "channel":"qidian", "ts":"…", "trace_id":"…",
  "payload": { "state":"login_required", "state_code":"WAIT_SMS", "state_reason":"等待短信验证",
               "error_since_ms": null,                 // 🔴 R6-4:基线 §7.1 Account 信封顶层字段,INTEGER epoch ms
               "prompt": { "kind":"WAIT_SMS", "text":"请在画面里输入手机收到的验证码",
                           "qrcode_png_b64": null, "expires_at": null, "countdown_s": null },
               "login_session_id": "ls_01J9…" } }   // 基线 N-3:标识本次登录尝试(格式 `ls_`+ULID,§6);进入登录流程即带、结束(成功/失败/取消)即失效
```
⚠️ **`error_since_ms` 语义(🔴 R6-4)**:**仅 `state=error` 时非空**——账号迁入 `error` 的那一刻写当前 epoch ms,迁出 `error`(→`running/degraded/stopped` 等任一非 error 态)即置 `null`;其余任何 `state` 下恒 `null`(上例 `state=login_required`,故为 `null`)。它与 `GET /accounts*` 出参、基线 §7.1 Account 信封**同名同义同值**,落库形态是 02 `account_runtime.error_since_ms`(§3.1)。**控制台只认这个信封字段**:`P-ACCT` 微信组「已故障 N 分钟」= `(now − error_since_ms)/60000`、「强制释放并切换」按钮灰态 = `now − error_since_ms ≥ [wechat] slot_error_takeover_s×1000`(01 §2.7.3、`qt-acct-wechat-holder-fault`/`-force-release`);**不读库列**。没有它,01 的故障态文案与按钮灰态不可编码(R6-4 原判词)。
⚠️ **`login_session_id` 语义(基线 N-3)**:它是**一次登录尝试**的 id,不是「无 `account_id` 时的替代主键」——`account_id` 已恒有(R-23)。三通道进入登录流程即生成、贯穿该次尝试的全部 `prompt`/`account_state`、结束即失效;同账号连续多次尝试(二维码过期重扫、取钥失败重试、超时重来)各有各的 `login_session_id`,前端据此判「这条 prompt 属于哪次尝试」,避免上一次的过期二维码盖掉这一次;`login_cancel` 按它定位那次尝试。**非登录态事件该字段为 `null`**。

## 6. 安全与合规

### 6.1 `P-SETUP` 合规告知页要点(以下为**告知正文要点**,读完后勾**一个**「我已阅读并理解」复选框即可继续——**不是逐项勾选**)

1. **账号归属**:本机登录的每个企点/QQ/微信账号都是使用方自己的、有权自动化的账号;不得用于他人账号。
2. **风控与封号风险**:模拟设备身份(企点)、批量自动化、多账号同 IP、UI 自动化(微信)可能违反各平台用户协议,存在被风控/封号的风险,由使用方承担(主文档 §3.3 合规提示)。
3. **凭据保存**:勾选"保存到保险库"的账号密码以 Windows DPAPI 加密存在本机,管理员可解;绑定本机,不可迁移;可随时删除。
4. **微信读取方式**:微信通道通过解密本机微信数据库读取消息、通过 UI 自动化发送;需要开启讲述人一次、在线期间本机不休眠(锁屏由你的设置/公司策略决定,锁屏期间不能发送);企业微信不支持。**微信通道与 WSL 里的服务随 Windows 用户登录后启动,未登录桌面时不会自动运行、账号不会自动恢复**(A-7);启用微信模块后本机电源计划改为不休眠(关闭模块时还原,C-6),并在系统 hosts 里屏蔽微信更新域名(卸载时删除,B-2)。
5. **消息留痕**:消息正文按账号级开关进本地消息库,按保留期删除;日志与审计不含正文与密码。
6. **不绕过验证、不自动重登**:短信、滑块、扫码、设备确认一律由人完成,系统不做任何绕过;账号掉线后系统只提醒,**不会用保存的密码自动重新登录**,需要你在控制台点「登录」(D-2)。
7. **对外接口**:开放局域网/公网 API 时的鉴权与审计责任(主文档 A.6/D.3)。

**滚到底 + 勾上那一个「我已阅读并理解」确认框**(01 `qt-setup-notice-ack`)才能继续,未勾 ⇒ 不进入首登引导(R5-8 老分叉①:单个确认框,非逐项);勾选记录(时间、控制台版本、告知页版本号)落 `audit_log`,告知页文本改版则要求重新勾选。

### 6.2 安全要点汇总
- 凭据:§2.2 全部;WSL 侧唯一明文 = `agent` 令牌(`0600 root`)。
- 二维码 PNG 只在事件里飞一次,不落盘;`GET /accounts/{id}/prompt` 重取时重新向 NapCat 取新码而不是缓存旧码。
- 画面流与截图含业务信息:`login_required` 期间的截图不进审计,只进事件。
- 微信槽位切换必须先排空写指令,杜绝"指令发给 wx01、实际微信已是 wx02"。
- 档案不可变 + 卷即身份:任何"修复"手段不得改档案;需要新设备就新建账号。
- `DELETE` 恒软删保留卷;真删是独立端点 `purge`,body `confirm` 必须等于 id 原文(对话框 + 输原文双确认)。
- 控制台令牌只存 Vault、经服务侧命名管道签发,渲染进程零秘密(C-04)。
- 昵称/群名等只用于展示与机构识别类逻辑,不作为鉴权依据。
