## 0. 标注含义(为什么这三类危险)

| 标注 | 含义 | 危险在哪 |
|---|---|---|
| **🔴** | 值冲突 / 归属冲突 —— 同一键在两处给了**不同默认值**,或落在了**不同的 owner 文件**,或与基线裁决相反 | 实现者读哪一册,就得到哪个答案 ⇒ **两套运行行为**。这是四路评审里唯一「跑起来会不会不一样」的一类。 |
| **(a)** | 同值双写 —— 同一键在两处定义、**当前值一致** | 现在不炸,但违反 §11.10 [CFGSRC]「一处定义他处引用」;哪天改一处忘另一处,立刻降级成 🔴,且**没有护栏会提醒**。 |
| **(b)** | 键名分歧 —— **同一个设置**,在**同一个文件、同一个段**里被写成**两个不同的键名**(值可能一致) | 最隐蔽:名字都不一样,**grep 都对不上**,双写检查也发现不了。代码读其中一个名,配置写另一个名 ⇒ 读到的永远是默认值、写进去的永远不生效,**静默半失效**。 |

**单一来源原则(基线 §11.10 [CFGSRC]):同一项只在一处定义,他处引用。** 归属判据(基线 R3,你已拍板):**「谁做决策谁持有」,不是「谁执行动作」**——例:微信槽位 reaper、登录超时→状态机转移都是 Agent 的决策,故 `slot_pending_ttl_s`、`switch_drain_timeout_s`、`qr_max_wait_s` 归 `agent.toml`,即便执行 UI 动作的是 WinAgent 会话代理。

## 7. `[retention]` 两侧独立性(基线 R3-38 通则)

`[retention]` 两段(agent.toml / winagent.toml)**默认独立、不要求相等** —— 不同库、不同数据类,红线(§11.10)只给「≤30」上限;强行绑等值反而错(`wa_audit_days` 与 `messages_days` 不是一个量,`probe_results` 可比消息更短)。

**唯一例外:`health_samples` 三级降采样档(`raw/1m/1h`)两库必须逐档相等。** 它是唯一一个「两库同名 + 查询期合并成一个视图」的表(agent.db=WSL 侧样本、winagent.db=Windows 侧样本,P-RES 查询期合并成一条曲线,04 §3.1 health_samples(两库合并曲线))。两侧保留深度不同 ⇒ 合并曲线一半 90 天、一半 30 天,历史深度不对称 = 坏图。故三档必须两库逐档相等(02 §2.8.4 亦述「两库同规则」)。**这正是 C2 必须两库一起改 30、不能只改一处的原因。**
