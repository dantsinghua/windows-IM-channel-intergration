## 2. 冲突清单

### 2.1 幂等 / 会话身份 / 消息去重(实现分叉级)

**C-01 🔴 `idempotency` 主键与邮件 `req_id` 的作用域**
- 涉及:06 §2.5 去重与幂等、§2.8 映射表、§9.1;02 §3.1 `idempotency` DDL(`PRIMARY KEY (account_id, idem_key)` + `args_hash`);00 §6(`idempotency_key` 调用方给,邮件 `req_id` 落同一字段)。
- 06 说:两个发起方各自从 `0001` 编号会撞;提议主键 `(actor, key)`,或 Transport 进总线前把邮件键改写为 `mail:{sender}:{req_id}`;同 `req_id` 不同正文**仍按幂等命中、不执行**,回执写"ID 已被使用且内容不同"。
- 02 说:主键 `(account_id, idem_key)`,`args_hash` 不同 → `INVALID_ARGS`。
- 基线说:C.4.3 语义 = 同 key 重复请求直接返回上次结果;字段由调用方给。
- 结论:两种键下 C.4.3 语义都成立,但 `(account_id, key)` 下**跨发件人撞键**会把别人的结果当自己的重放(同参数时)或被判 `INVALID_ARGS`(不同参数时)——前者是静默错答。02 的 `args_hash` 拒绝与 06 的"不执行、回执说明"其实是**同一件事**(码都是 `INVALID_ARGS`,06 §9.8 已认),不冲突。
- 建议裁决(**v1.1 §6 已按此定**):保留 02 DDL 不动,`Transport(email)` 进总线前把 `idempotency_key` 改写为 `mail:{发件人短名}:{req_id}`;余项:06 §2.3.2 `指令ID` 上限从 ≤128 收到 **≤64**(前缀 + 短名 + `:` 后仍 ≤128 才过 02 的 CHECK),且"发件人短名"要定义(建议 = `[mail.inbound.hmac]` 表里该发件人的键名,与 Vault 路径 `hmac/<短名>` 同源)。理由:改主键要动所有入口,改写键只动一个入口。

**C-02 🔴 出向消息何时入库、确认态放在哪张表**
- 涉及:06 §2.12 发送确认对消息库的依赖、§3.1 `messages` 补列(`state/confirmed_by/confirmed_ms/idempotency_key`);02 §2.8.1 第四行"出向(我方发)…`DELIVERED` 时 `ingest(dir='out')`"、DDL `messages.ext_msg_id NOT NULL`、`command_results.confirmed_by/confirm_ms`。
- 06 说:调通道**之前**先插一行 `state=SENDING、ext_msg_id=null`,读回命中后改 `DELIVERED`;入向轮询撞到自己发的 → 合并进这一行;`state` 只对 `dir=out` 有意义。
- 02 说:只在 `DELIVERED` 时入库,`ext_msg_id` 取确认拿到的原生 id(NOT NULL);确认态在 `command_results`。
- 基线说:§7.4 `Message` 没有 `state`;§7.3 `CommandResult` 有 `source/code`。
- 结论:两边同时实现 → `messages` 一边有 SENDING 行一边没有;`ext_msg_id NOT NULL` 直接让 06 的预插失败。确认态在两张表各存一份也会漂。
- 建议裁决:**v1.1 已定 `Message` 带 `state`(99 C-21),按 v1.1 执行**——02 DDL 必须跟着改:①`messages.ext_msg_id` 改可空(SENDING 行没有原生 id),唯一键改部分索引 `WHERE ext_msg_id IS NOT NULL`;②加 `state TEXT CHECK (state IN ('SENDING','DELIVERED','UNCONFIRMED','FAILED'))`(`dir='in'` 恒 NULL)、`confirmed_by`、`confirmed_ms`、`idempotency_key`;③02 §2.8.1 出向行改为"调通道前插 SENDING 行,确认后更新";④`command_results.confirmed_by/confirm_ms` 与 `messages.state` **二选一留一份**(建议留 `command_results`,`messages.state` 由它派生写入,避免两处漂),02 写明谁是源。
  **复议意见(供总控)**:本文原倾向反向——确认态只在 `command_results`、`messages` 只落已达消息;06 §2.12 的两条价值(①UNCONFIRMED 后被轮询读到的自消息要"认亲";②幂等重试前查是否已发出)可改为:入向 `self=true` 消息入库时查 `command_results.code='SEND_CALLED_BUT_UNCONFIRMED'` 且同 `session` + `text_hash` 相等 + `|ts−finished_ms| ≤ 60s` 的行 → 回填 `messages.trace_id`、result 改 `DELIVERED`、发 `command_done` 更新事件。理由:`messages` 里放半条未发出的消息会进 FTS/导出/信息邮件(06 §2.4.3 订阅 `dir=out` 事件——SENDING 行若也发事件,失败的发送也会被当"信息邮件"发出去,06 §2.4.3 得再加 `state=DELIVERED` 门槛)。若总控维持 v1.1,请至少把这条门槛写进 06 §2.4.3 与 02 §2.2.7。

**C-03 🔴 `messages` 去重唯一键**
- 涉及:06 §2.9.2 去重键、§3.1 `messages`;02 §2.8.1 表格与 DDL `UNIQUE (account_id, ext_msg_id)` + `ON CONFLICT … DO UPDATE`。
- 06 说:有原生 ID 用 `(account_id, session_id, ext_msg_id)`;QQ `message_id` NapCat 重启后可能复用,同键命中还要比 `ts`(差 > 1h 当新消息、后缀 `#2`);微信 `ext = str(seq)`;无原生 ID 用 `fingerprint`。
- 02 说:`(account_id, ext_msg_id)`;微信 `ext = "{talker}:{seq}"`;企点无 id 时 `ext = sha1(session|sender|ts_minute|text_hash)` + `dedup_kind='anchor'`;冲突即 UPDATE。
- 结论:按 02,QQ 重启后复用的 `message_id` 会 **`DO UPDATE` 静默吞掉新消息**(只补 revoked/text,新消息一行不留)——这是 06 点名的坑;`session_id` 不在键里,跨群同号也撞。
- 建议裁决:02 唯一键改 **`(account_id, session_id, ext_msg_id)`**(与 `sessions` FK 同源,索引 `ix_messages_session_ts` 已按 session 组织);微信 `ext` 统一 **`str(seq)`**(talker 已在 session_id 里,不再重复拼);QQ 的"同键 ts 差 > 1h 当新消息"写进 02 §2.8.1 `ingest` 规则(命中且 `|ts_ms 差| > 3600_000` → 新行 `ext_msg_id = ext + '#' + n`);企点锚块 hash 保留 02 的 `dedup_kind='anchor'` 命名,06 的 `fp:` 前缀作废(一个概念一个名)。`fingerprint` 列另见 C-05。

**C-04 🔴 `mail_inbox` 没有 `nonce` 列——防重放没有落点**
- 涉及:06 §2.3.4 防重放(`(sender, nonce)` 唯一、`nonce_ttl_h=24`)、§3.1 `mail_inbox.nonce`;02 §3.1 `mail_inbox` DDL(无 `nonce`)。
