# 本地服务告警与微信取钥整改方案（待安琳审批）

本轮仅完成只读诊断和方案设计，尚未改产品代码、补部署文件或重新执行取钥。当前范围为本机 QTrade 测试环境及同版程序在其他电脑上的同类问题；MQ 认证仍按此前决定跳过。

| 问题 | 本机已确认的证据 | 其他电脑是否会发生 |
|---|---|---|
| WinAgent、Docker 告警与实际状态不符 | 22:56 的真实 health 为 H02/H03=ok、WinAgent/UserAgent 在线、dockerd=true、当前 alerts=[]；Windows 服务及 guest Docker 均 running。但持久事件中这两项最后状态仍是 firing，分别来自 17:38:05、20:26:26 | 会。故障期间 Agent 退出或重启后，内存 active 被清空，持久 firing 仍可重放；当前 resolve() 找不到内存项便不发恢复事件，客户端会继续把旧故障显示为当前告警 |
| 微信第六步“起 hook”未成功 | 本地 `QTrade-E2E/pkg/chatlog` 目录缺失。22:20:19 的用户代理日志明确报 chatlog.exe 不在位；此次在文件存在性检查处就失败，尚未复制 DLL、启动取钥工具或注入 | 本次直接原因是准备本地测试环境时漏部署资产，应由本轮环境准备纠正。最终安装包中 chatlog.exe、两份候选 DLL、ffmpeg.exe 齐全；其他电脑若遇到不完整部署、文件被隔离/误删、目录权限或路径配置问题，仍会触发相同失败 |

本机微信进程存在，文件版本为 4.1.12.26，与随包版本相同。已经打开微信不能补足缺失的取钥程序。当前失败链路会先释放 pending 槽位再写 stopped，没有必须删除账号、清空数据库或重启微信才能解锁的证据。

诊断证据在 `.codex/local-health-wechat-20261013-14ha3cxp/`：`current-health.json`、`guest-readonly.json`、`user-log-redacted.txt`、`wechat-version.json`。未读取或输出真实密钥、聊天正文。

建议按以下三部分实施，复用现有告警机制、登录会话和部署清单，不新增依赖、数据库表或通用任务框架。

1. **让告警恢复真正闭环。**
   - 在 Agent 重启后的首次实际健康确认中，对 H02/H03 做一次恢复校正，复用已有 `Alerts.settle()` 补齐需要的恢复事件。探测失败或结果未知时不能清掉真实故障；后续保持现有 H02 去抖和状态变化去重。
   - 只有恢复事件成功记录后才完成校正；连续健康探测不重复刷恢复事件。保留原故障历史，不直接修改或删除数据库告警来制造正常状态。
   - 前端区分正在故障、已恢复及历史回放。服务端沿用订阅时捕获的 `subscribed_after`，给每条带 seq 的 WS 事件增加仅传输层字段 `replayed = (seq <= subscribed_after)`；不写入 outbox、不改变业务 payload 或二维码隐私边界。前端仍归约全部合法事件来恢复状态，仅对 `replayed === false && state === 'firing' && severity === 'crit'` 弹故障通知；字段缺失时继续展示状态，但不猜测是否为新通知。同步规格、事件类型、服务端产生方和前端通知消费方，保持旧客户端可忽略新增字段。
   - 回放分界只依据服务端 seq，不依据连接 open、客户端时间或固定延时。回放尚未结束时产生的新故障仍属于实时事件。截断通知中的 `from_seq` 表示第一条可回放事件，前端去重水位应设为 `from_seq - 1`，避免当前实现将边界第一条丢掉；过滤、截断、重连均纳入回归。重连后应与恢复事件收敛，不能重新出现已结束的告警。
   - 本次不加入自动重启 Docker。当前 Docker 正常，这与既有 H03 自动恢复策略待办是不同事项。

2. **补齐部署资产，失败时给出可操作结果。**
   - 按已验安装包清单和哈希补齐本地测试环境的工具；以后本地包环境准备也执行完整资产核对，不能只复制桌面和 WinAgent EXE。
   - 取钥开始前检查该动作必需的 chatlog.exe、实际选用的 DLL、工作目录权限及受支持版本。路径继续由实际安装根和用户配置解析，不写死本机用户名、盘符或微信目录。
   - 缺件、访问拒绝、工具启动后立即退出等情况返回稳定的错误码/原因，登录会话进入明确失败状态。GUI 停止等待，显示原因，并用既有 Agent 启动入口重试原账号；不新建第二个档案，也不绕过槽位和身份绑定直接调用底层取钥重试。
   - 保留已经正确的 pending 释放逻辑。第六步由真实会话状态驱动，不再仅凭目录存在/缓存的 logged_in 值认定正在起 hook；进程启动也不能冒称已经取到密钥。
   - ffmpeg 属于完整部署资产，但其缺失不应被误说成取钥工具缺失；运行时检查按实际功能依赖执行。

3. **补同一链路的跨环境防护。**
   - 无法确定可信的目标 PID 时明确失败，禁止落到不带 `--pid` 的交互选择器等待。多进程、权限不足、非标准安装位置分别给原因；兼容范围外的微信版本明确告知，不扩大承诺支持范围。
   - 将耗时的进程/文件句柄探测与用户代理事件循环隔离，一次最多一个在途探测，保持心跳可响应。探测线程只返回候选结果；真正写 DLL、启动工具前，必须在事件循环中重新核对会话、操作归属、取消标记和截止时间，不能让超时后的旧线程自行启动 hook。
   - 共用工作目录、DLL、取钥子进程由现有微信管理对象内的一把操作锁保护，范围跨登录会话；用 `login_session_id` 加本次操作标识确定归属，不增加通用锁服务。锁只覆盖起停、换 DLL 等变更操作，不覆盖整个登录会话；成功启动后记录子进程归属并释放本次操作锁，允许后续状态推进。相同操作的重复请求返回当前快照或合并等待，不排队后再执行一遍。取消先使旧操作失效；取消/超时的变更操作只有在旧线程实际返回、相关子进程完成收尾后才释放资源锁，HTTP 超时或协程取消不等于线程已经退出。
   - 旧操作未退场时，新会话/重试明确返回“前次操作正在收尾”，不得覆盖 DLL 或启动另一轮；读取快照、心跳和取消标记保持可响应。旧操作迟到只能释放自己持有的操作标识和资源，不得覆盖新会话或清除新标记。清理使用启动时捕获的子进程对象/PID 及创建身份，禁止按进程名扫描停止或重新读取全局“当前 PID”。若底层调用持续不返回，显示资源仍被占用和诊断原因，不持续显示“起 hook”，也不自动强杀微信或重启服务。
   - 时限按端点设置，不能统一成同一个值：`login/start`、`key/retry` 保留 Agent HTTP 65 秒、服务等待 60 秒、用户代理 59 秒；由 Agent 驱动的 `status/login-status` 调整为 15/10/9 秒；控制台纯快照读取为 5/3/2 秒。内部动作截止必须早于用户代理响应截止，给错误传回留余量；需要继续收尾的底层操作遵守上一条资源锁规则。当前 5/10/9 秒错配仅指状态链路，不能因此缩短已有慢启动预算。对会推进状态的请求禁用无条件传输重试，真正只读快照保留有界重试。限制只施加于微信操作，不锁整个管道或健康探针。
   - 页面只读取状态快照，由现有后台登录流程负责推进；推进权限/调用来源由服务端确定。保留现有状态机，不直接删掉 poll() 使登录无法前进，也不把控制台刷新当成一次新的取钥操作。
   - DLL 被占用时，能证明同一份文件才复用；需要切换却无法完成时必须真实报告，不能以旧 DLL 冒充新候选。取消/失败只处理本次所属的取钥子进程，不默认关闭微信或宣称已卸载微信进程中的 DLL。

第三部分中的 PID 探测阻塞、无 PID 交互分支、时限错配和重复推进是源码确认的风险；本轮现场并未走到这些位置，不能把它们写成此次缺件故障的已证原因。

验收以同一修复版本为准，先复现旧行为，再验证修复，不使用历史通过次数替代本轮结果：

| 验收场景 | 必须观察到的结果 |
|---|---|

| WinAgent 或 Docker 仍故障、探测未知、恢复事件写入失败 | 不假报恢复；H02 原防抖保持；写入失败仍可重试校正 |

| chatlog/DLL 缺失、损坏、无权限 | 有明确终态和原因，页面不再停在“起 hook”；pending 正常释放；补齐后可重试原账号 |

| 启动、重试、推进状态、纯快照各自逼近时限 | 内层先返回明确错误，外层留传回余量；启动仍保留 65/60/59 秒预算；响应超时不提前释放仍在执行的资源 |
| DLL 占用或工具启动后失败 | 显示实际使用/失败状态；不假报替换、hook 成功或取钥完成 |
| 本地部署及新版组件 | 资产哈希完整；前端、Agent、WinAgent 使用同版代码；相关回归、完整组件检查及本地联动验证通过 |

真实取钥成功和读取服务就绪要在安琳批准后结合当次微信会话验证；如确需微信重登、关闭或切换版本，须先说明该动作及影响，不能从本方案审批推定授权。诊断阶段没有调用会推进取钥的微信 status 接口。

实施前需安排短暂的 QTrade 维护窗口：本次只读检查显示本地已有 1 个运行中账号，替换前后端/用户代理可能中断采集或需要重连。应先核在途操作和专用 WSL 的保活/恢复边界，落盘本次组件精确停启、备份及失败回退清单，再部署；部署后检查原账号采集恢复。不清空现有账号、配置、聊天数据或 Vault，不把此次修复扩大为全局 WSL/Docker 重启。
