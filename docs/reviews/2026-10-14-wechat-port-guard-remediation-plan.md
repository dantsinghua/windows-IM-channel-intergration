# 微信取钥端口误判：根因与修复方案（待安琳确认）

安琳最新要求“还是失败，请继续定位根因发我确认”。本文件是待审批方案；该指令之后只进行了只读诊断，没有继续修改产品、部署、重试 hook 或启动总安装包构建。

## 已确认的根因

本次失败是前一轮新增端口保护引入的回归。模块已启用、用户代理在线、微信 4.1.12.26 版本匹配，四份取钥资产也已补齐；新的失败发生在启动工具之前。

真实向导发起后，`wx03` 进入 `stopped`，服务返回 `409 BUSY / wechat_chatlog_port_in_use`。页面已正确显示终止原因，但原因“端口已被占用”不符合现场事实。

| 本机只读检查 | 结果 |
|---|---|
| 5030 的 TCP 监听表，探测前后 | 均没有 LISTEN 记录 |
| 对 5030 等待 0.2 秒 | 0.219 秒返回 10035 |
| 对 5030 等待 1 秒、2 秒 | 分别约 1.016 秒、2 秒返回 10035 |
| 对 5030 等待 3 秒、5 秒 | 分别约 2.062 秒、2.047 秒返回 10061（连接被拒绝） |
| 对实际监听的 WinAgent 17610 探测 | 约 0.015～0.016 秒连接成功 |
| 普通用户直接读 TCP 监听表，三轮 | 5030 无监听；17610 的监听属主均为实际 WinAgent PID 34484 |

Windows 的 10035 是 `WSAEWOULDBLOCK`，表示操作未能立即完成，不能证明端口被占用；`connect_ex` 返回连接操作的错误指示，且受超时设置约束。参见 [Microsoft Winsock 错误说明](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2) 和 [Python 3.12 socket 文档](https://docs.python.org/3.12/library/socket.html#socket.socket.connect_ex)。约 2.05 秒是本机这轮观测，不是所有 Windows 的固定时限。

源码存在两处相连的错误：

1. `WinWeChat._port_in_use()` 只等待 0.2 秒，将所有非明确拒绝的返回值折成“占用”，丢失了“结果未知”。
2. `_reserve_start(mode)` 对 `key` 和 `server` 一律检查 HTTP 端口。取钥动作因此继承了后续读取服务的依赖，在写 DLL、启动 `chatlog key` 之前被阻断。

其他 Windows 机器只要空闲端口的拒绝结果晚于 200ms，就可能复发。此次没有证据支持关闭其他程序、修改防火墙或重启网络。前一轮 Windows 全量用的是假后端，覆盖了错误码分支，却未覆盖真实空闲端口的延迟拒绝以及 key/server 的依赖分层；这属于本轮验证遗漏。既有测试通过记录保留，但不能当作真实取钥已通过。

## 建议的最小修复

1. **按动作保留必要检查。**`key` 继续校验工具、DLL、工作目录、目标微信进程和受管进程归属；不查询后续 HTTP 服务端口。`server` 才检查其实际监听端点。保留已有跨会话操作锁和异常遗留进程记录。
2. **读取 Windows 的实际监听表。**复用现有 `psutil`，区分“发现监听”“完整查询后未发现监听”“查询失败或无法判定”。查询放入既有有界工作线程，保留取消后等待实际退场的规则，不新增依赖或任务框架。未知结果对 server 明确报“无法核实”，不能冒称占用或允许重复启动；它不成为 key 的依赖。
3. **精确匹配地址和进程。**依据配置中的 `127.0.0.1:<port>` 及会冲突的通配监听判断，不能仅凭端口号把其他不冲突的本地 IP 算成占用。IPv6 通配监听无法判定双栈冲突时保持未知。查询失败、不完整结果、无法识别属主均不得当作完整的“没有监听”。
4. **实际就绪才算启动成功。**前置检查没有监听只允许尝试启动；随后还须验证本次受管 Process、PID 和创建身份、预期回环端点的监听属主及健康响应。检查后被抢占、绑定失败、进程退出、他人服务返回 HTTP 200，都不能冒充本次服务就绪。只清理本次所属进程。
5. **沿用总时限并说明真实阶段。**停旧、查表、启动、就绪检查共用同一剩余 deadline，不能把每一步时限相加，也不整体延长现有接口预算。错误区分取钥与读取服务阶段、真实占用与查询未知；页面展示可理解的原因，技术请求路径和原始错误信封留在脱敏诊断记录中。保留已有密钥，不因端口诊断失败删除它们。

不建议仅把 0.2 秒改成 3 秒：这既没有修正 key/server 分层，也可能与最长约 6 秒的旧进程退出耗时相加，超过状态推进的 8 秒动作预算。其他电脑的延迟也未必相同。

## 放行标准

| 场景 | 必须观察到的行为 |
|---|---|
| key 模式，端口查表不可用或该端口被其他服务监听 | 不调用 HTTP 端口检查；仍须通过工具、PID、目录及受管进程归属检查 |
| server 查询完整且无相关监听 | 允许尝试启动；尚未把状态标成就绪 |
| 真实占用、权限拒绝、不完整结果、IPv6 冲突不明 | 原因准确；不误报空闲、不结束其他进程 |
| 检查后端口被抢占、旧 PID 重用、外部服务返回 200 | 本次服务不能被判成功；只处理本次受管对象 |
| 停机较慢、查表较慢、取消及重复请求 | 使用整轮剩余预算；心跳保持，旧任务未退场不放开资源 |
| 本机原生空闲端口与当前微信 | 复现本轮误判后，修正版真实进入取钥流程；不能用新增假件通过代替这一项 |
| 完整回归及成品 | 独立维护反例，同版回归、重新编译、源与成品绑定通过后才进入总装 |

进入 hook、取到两把密钥、读取服务就绪是三个不同验收点。需要打开图片或退出微信重新登录时，明确记录所处阶段；关闭微信、重登或切换版本仍须取得该具体动作的确认。
