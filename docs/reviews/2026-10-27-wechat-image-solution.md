## 2. 逐项修复内容

### 2.1 恢复图片引用和下载合同

修改[微信归一化](../../src/qtrade_agent/adapters/wechat/normalize.py)与[媒体模块](../../src/qtrade_agent/media.py)，同时承接真实的 `contents.md5/contents.path` 和已有顶层格式。先校验字段类型、账号来源、合法资源标识及路径归属，再生成统一的内部媒体描述。

内部下载字段以下载器现有 `wa_path` 合同为基础统一，旧 `ref` 只能在明确的微信同源路径范围内兼容转换；不得把任意URL或本地路径直接交给下载器。原始图片引用只用于原生资源定位，传输内容身份另以**解码后图片字节的 SHA256**表示，两者不能混为一谈。

需要一并修复内容去重后的引用重绑：如果媒体任务命中已有图片，应在同一事务内将消息和任务引用改到保留的 media ID，再处理临时记录；不得出现文件已下载但消息指向已删除 media ID 的情况。

### 2.2 先解决原图404，再推进模型链

只读诊断已经证实配置根路径不匹配：现役 Chatlog 的 `data_dir` 是当前账号的 `db_storage` 子目录，原生媒体相对路径却从账号根开始。在配置根下匹配图片数为0，在同一账号根下为3。图片密钥字段存在，但这不能证明密钥正确或V2解密成功。原路径和组合引用探针均返回404，不能将其解释为未下载。详见[404诊断及修复分支](/home/anlin/.local/state/qtrade-image-20261027/solution/404/REPORT.md)。

首个最小候选是在 [WinAgent媒体后端](../../winagent/src/qtrade_winagent/win/wechat.py) 的 `discover_chatlog_data_dir()` / `_prepare_server()` 中分开“数据库探测目录”和“媒体资源账号根”：继续用数据库目录验证数据就绪，将同一已核实账号的资源根用于server。只有同版配置合同明确支持独立媒体根时才使用对应字段，不发明配置项。保持当前账号UID、受保护键引用与登录态，受控更新reader后验收。

目前没有取得同版Chatlog内部HTTP处理器源码，也没有实际应用根目录候选，因此不能称“改根已证明恢复”。三个放行门必须分别通过：

| 门 | 必须取得的结果 |
|---|---|
| 数据库仍可读 | 原账号UID、进程及键引用一致；目标群文字、联系人、会话和游标增量保持可读，无历史重放 |
| 媒体唯一定位 | 原生md5/path共同定位当前账号根内的唯一资源；路径规范化后拒绝越界、UNC、其他账号及链接逃逸 |
| V2完整解码 | 正式接口返回明文图片，完整解码可读取宽高，MIME/大小/SHA一致；拒绝HTML/JSON错误、加密DAT、损坏图片及假200 |

如果修正根后仍404，按新证据查资源索引；能定位但解密失败时，核验当前账号绑定的有效Image Key及V2兼容性，不先重取密钥、重登或换版掩盖路径问题。

可优先复用旧资源包已有的V2解码和高清资源定位能力，但必须在WinAgent内部收口：移除“取任意历史img_key”的回退，只接受当前账号资源句柄；保留 `hd/thumb/orig` 来源标识。原图或经过质量验证的高清图才可进入正式识别；缩略图仅预览并等待原图，不能冒认原图。对 `wxgf` 等特殊内容不得盲目转码后仅凭退出码当成功；必须完整解码验证。若需要缩放或分片，保留原图及变换关系，为每个派生图单独记录摘要。

### 2.3 将图片采集事实与发送归属分开

推荐为仅解析消费者增加隔离的 `capture-only` 用途，复用现有认证、加密文件传输及附件编码。该用途接收授权群中的原生采集事实，不参与自动发送、人工接管判断或发送回执确认。

旧控制链继续保留 `UNKNOWN`、发送闸、manual fence 与精确命令归属检查。禁止通过清除UNKNOWN、伪造human、伪造 `source_command_id` 或直接把waiting改为published来放行图片。

推荐采用以下**拟议合同**，经生产方和南银承接方共同冻结、独立验收后才能实施；它尚未发布：

| 项目 | 推荐规则 |
|---|---|
| 用途与方向 | 版本化用途 `purpose=wechat-capture-v1`，独立、固定派生的 `capture_up/capture_down` 路径；复用现有Codec、journal、附件分块和ACK，不投入旧询价event队列 |
| 接收权限 | 消费者固定为 `consumer_id=nanyin-deposit-parser`；由已认证管理员按机构/owner、工作台、通道、稳定账号UID、消费者及选中群版本签名授权；未知用途拒绝 |
| 事件类别 | 区分 `capture_fact`、`capture_media`、`capture_attribution`；南银handler只推进采集、媒体和解析任务，不改旧command、上下文watermark、fence，也不触发发送 |
| 消息身份 | `capture_id`沿用现有微信稳定身份核心：工作台、账号UID、peer、原生ext_msg_id；不包含槽位、群名或图片SHA。同图两次发送是两条原生消息，不能因内容相同被合并 |
| 附件版本 | 同capture_id下维护 `content_revision`、`media_revision`及附件顺序、大小、MIME、SHA；补全使用新的wire事件ID及更高修订号，不制造新业务消息 |
| 未知归属 | 未知时仅记 `attribution.status=unresolved`，不写假source_command_id；取得精确原生映射后只补关联，不改UNKNOWN、不因归属补注新建解析任务 |
| 持久化与ACK | 复用原生入库事务内outbox，保证采集事实先可靠落盘；接收ACK只表示可靠接收，不代表模型成功。采用至少一次传输与幂等业务提交 |
| 解析幂等 | 以 `(capture_id, content_revision, media_revision, workflow_version)` 约束有效解析提交；保存run ID，优先查询同次结果后决定重试。超时丢响应可能重复调用远端模型，但同版本业务结果只能生效一次 |

南银收到元数据后处于 `WAIT_MEDIA`，完整附件通过校验后才进入 `READY_PARSE`。这些是拟议媒体就绪状态，不替代旧发送状态。现有控制流与新采集流双轨期间，要按相同稳定身份去重，避免一条消息落成两份ODS。

先部署具备新用途识别能力的承接方，再由生产方协商确认能力；首次仅对Greydan灰度启用。旧询价消费者不订阅新路径，旧承接方不接收未知schema，不做隐式降级。

这部分涉及共享合同；本方案不直接修改或发布对端协议。生产方与承接方的联合验收通过，是自发图片全链放行的前置条件。

### 2.4 让附件补全和传输可恢复

图片记录与附件就绪分开处理：记录可先建立，只有附件完整、摘要一致且可解码时才进入图片解析。上传和消费沿用现有journal、ACK及分块机制；达到现有内联阈值后走分块重组，不能在发送失败后丢弃任务或重造消息身份。

媒体更新必须能触发附件修订。当前[host观察路径](../../src/qtrade_agent/ossbox/xunjia_v22.py)只比较正文和撤回状态，无法保证历史 `media=[]` 记录自然补全。需要将媒体指纹/版本纳入更新判定，并为已存在的消息建立附件跟踪；只有字节或有效媒体状态变化才产生修订，重复扫描不无限发布。

消费者只在完整附件落盘和SHA校验通过后确认可解析状态。文件大小限制取采集端、文件网关、本地Dify和上游模型约束的共同可接受范围；超限必须明确报错或走经过验收的派生图处理，不静默截断。

## 4. 历史恢复、影响范围和回滚

历史补全默认只处理本次目标图片及后续明确列入清单的消息，不全库重扫。补全前冻结消息、附件及事件账本前像；读取原生事实后在账号身份和记录版本仍一致的条件下补充媒体，并通过正式修订和消费路径推进。图片相同的不同原生消息保留各自业务记录；同一消息同一媒体版本的业务结果幂等提交、只生效一次。

本仓修改涉及微信归一化、媒体存储/下载、WinAgent媒体读取、host媒体修订。南银涉及附件接收完整性、ODS媒体状态、Workflow调用与本应用图片分支；shim涉及视觉入参校验、多图处理及观测。共享协议仅增加明确的采集用途，QQ不因此新增文件网关能力。

回滚按批次冻结源码、组件摘要和配置前像；保留可重试任务和已落原图，不清journal或UNKNOWN。共享合同通过能力协商控制启用：回滚时停止新用途的生产和消费，保留队列等待兼容版本恢复，不能将capture-only事件送回旧控制队列。数据库如需增加字段，应采用可兼容迁移，不靠删库退回。
