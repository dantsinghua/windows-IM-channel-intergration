# 08 · 系统健壮性与可观测性改进

> 版本 v0.1，2026-10-15。依据 `00` §15g **R6-111** 裁决（三起真实故障的根因与修复设计）。本册为需求文档，实现由后续批次承担并经独立验收。

## 0. 背景与范围

三起真实故障（2026-10-14~15）暴露同一类缺陷：**健康检查「检测到了、但不会自己恢复」；状态机「只降级、不回升」；跨进程错误语义在管道层被丢失；日志不落盘导致排障只能反推。**

| 故障 | 直接根因 |
|---|---|
| 微信读取超时误判 `KEY_FAIL`、降级后停读、回填中断 | 读超时被当硬失败（`poll.py` 只认 `wechat_read_catching_up`）；`wechat_poll_all` 只轮询 `state="running"` |
| 企点 adb 通道僵死、读库不可用 | adb server 无任何恢复手段（协议故意无 `kill_server`）；H05/H06 只告警不动作 |
| QQ/NapCat 一直 `WAIT_QRCODE`、心跳恢复不回 `running` | 二维码失败无自愈；H08 恢复分支只解告警、不回 running；`transition` 无去重导致事件刷屏 |

## 1. 范围与不做

**做**：三条自愈闭环、状态回升、重试退避、故障分层、错误码拆分、可观测性（日志/审计/错误信封）。
**不做**：不改变 D-2「不自动重登」（微信/QQ 登录态只由人触发）；不改变企点旁路读库正线；不重画架构；不新增对外 REST 端点（仅新增状态码/配置键）。

## 2. 设计

### 2.1 微信读取超时（根因已实测量化定死，2026-10-15）

**实测根因**（chatlog 两钥就绪、`wx14` 账号现场复现）：**会话基数大 + 会话级时间过滤失效（用错字段）+ 每次请求新建连接**，三者叠加放大为超时。**不是** SQLite 写入慢（两天 2400 条入库 <1s）、**不是**单次消息查询慢（chatlog GIN 单请求约 0.5ms）。

| 层 | 实测证据 |
|---|---|
| ① 会话基数 | 账号 **≥500 个会话**（`session?limit=500` 截断；读取窗口去重 talker = **710**）：含公众号 `gh_*`、服务号、`openim`、企业微信 `qy_u`、折叠群 `@placeholder_foldgroup` 等长尾 |
| ② 时间过滤失效（核心 bug） | `wechat_read_page._scan` 用 `row.get("nTime")`（**字符串** `2026-10-15T08:46:56+08:00`）做 `isinstance(stamp,(int,float))` 判断 → 恒 False → 过滤跳过 → **500+ 会话全部逐条查询**（其中 **263 个 >48h 无消息**）。正确字段是 `nOrder`（epoch 秒，实测 `1792025216`） |
| ③ 每次新建连接 | `win/wechat.py:_get_items` 每次 `build_opener`，无 keep-alive 复用 |
| ④ 累积超时 | 07:45~07:52 共 **12015 次** `/api/v1/chatlog` 请求 → 远超 6s/9s/10s 预算 → 504 → 误判 `KEY_FAIL` |

**修复设计**：

1. **会话级时间过滤修复（核心 bug）**：`_scan` 会话过滤改读 **`nOrder`**（epoch 秒，正确字段），或正确解析 `nTime` 字符串；只对「窗口内有消息」的会话发 chatlog 请求。
2. **历史回看窗口 = 往前 12 小时（安琳确认）**：首次拿到两钥解密读库后，仅回看**往前 12 小时**的历史消息。配合 ①，12h 窗口内仅 **67 个**会话需查询（vs 500+），请求量降约 **7 倍**。
3. **HTTP 连接复用**：`_get_items` 复用单个 opener + keep-alive（chatlog 为本地 GIN server，支持 keep-alive），消除每请求新建连接开销。
4. **响应限制拉长（安琳确认）**：WinAgent 用户代理内部可续读预算 `seconds` **6s → 10s**；服务侧 `TIMEOUT_S["wechat_read"]` **10s → 30s**；Agent 侧 HTTP 超时须 **> 服务侧时限 + 余量**。
5. **读失败重试退避**：`wechat/read` 失败后按 **1:2:4:8:16 秒** 指数退避，**最多 10 轮、或累计超过 600s**，停止自动重试并告警提醒人工重启。避免「性能阻塞 + 拼命重试导致资源死锁」（安琳原话）。
6. **降级后保留读轮询**：`degraded(KEY_FAIL/WECHAT_READ_FAILED)` 仍拉 `wechat/read`（只读），写仍拒；读恢复后自动回 `running`。
7. **故障分层**：读失败 `reason` 区分 **WinAgent 管道超时(`user_agent_timeout`) / chatlog HTTP 失败 / 微信进程退出 / 其它**，各自给出可操作 `state_reason` 与提示。
8. **错误码拆分**：新增 `WECHAT_READ_FAILED`（消息读取异常），`KEY_FAIL` 回归单一语义「取钥失败」。

### 2.2 企点 adb 通道自愈

1. **自愈动作（安琳确认：只重启 adb server，不重拉容器）**：H05/H06 连续失败达阈值后，允许自动执行「**重启 adb server(16000) → 重连全部企点 serial → `ensure_root`**」。不 `docker restart`，容器登录态不丢。
2. `AdbBackend` 协议新增 `kill_server`/`reconnect_server` 能力（当前 `backends.py` 故意没有，需从红线清单转出）；受 `auto_recover` 与每小时上限约束。
3. 读库失败（`QIDIAN_DB_UNAVAILABLE`）复用同一自愈信号：先触发自愈、自愈仍失败才保持告警；不再「只告警不动作」。
4. **读库降级到控件树：明示砍掉（安琳确认）**：不再承诺「读库失效 → 自动降级到控件树/截图+OCR」这条路线（从未实现、仅注释承诺）。读库失效即 `QIDIAN_DB_UNAVAILABLE` 告警 + 读能力暂不可用，等待 adb/读库自愈恢复；`read_strategy` 的 `uiautomator/screenshot` 兜底语义随之退役（正文口径由 06 §2.9.5 / 02 §2.2.3 / 00 §8.1 承接，实现批次逐处同步）。

### 2.3 QQ / NapCat 自愈

1. **恢复回 running**：H08 心跳恢复后 `transition(..., "running")`。语义边界：**连接恢复 ≠ 自动重登**，不违反 D-2（不触发扫码、不重建登录会话）。
2. **二维码初始化自愈（安琳确认：回 running + 容器重试，N=10）**：二维码连续失败 **10 次** 后自动**重启 NapCat 容器**重试（只重启容器，不自动扫码/不自动重登）。
3. **transition 去重**：`accounts.transition` 在 `state/state_code/state_reason` 三者未变时跳过（写库前比对），根治每 30s/35s 刷一条 `account_state` 事件。
4. **`_qq_login_required` 改走 `mark_offline`**：补 `ACCOUNT_OFFLINE` 告警 + `offline_count_1h`/`last_offline_code`，与掉线语义一致。
5. 清理死配置 `[adapters.qq] heartbeat_timeout_s`（无消费点）。

### 2.4 跨问题：自愈动作分级 + 回升判据 + 可观测性

**自愈动作分级（统一框架，供各故障复用）**：

| 级 | 动作 | 适用 | 约束 |
|---|---|---|---|
| L0 | 仅告警 | 需人工决策/有数据风险 | — |
| L1 | 重连（disconnect+connect / WS 重连） | adb 单账号、OneBot 断连 | 退避、封顶 |
| L2 | 重启进程（adb server / chatlog server） | adb 通道僵死、chatlog 崩溃 | `auto_recover` + 每小时上限 |
| L3 | 重启容器（redroid / napcat） | 容器内进程不可恢复 | 同上 + 明确中断影响 |

**回升判据表（每个可恢复降级码的反向闭环）**：

| 降级码 | 回升判据 |
|---|---|
| `WECHAT_READ_FAILED` | 连续一次 `wechat/read` 成功且 chatlog `key_ok=true` |
| `KEY_FAIL`（取钥） | `key_retry` 成功、两钥落盘 |
| `SCREEN_LOCKED` | `status.screen_locked=false` |
| `H06_ADB_OFFLINE` | `adb devices` 该 serial == `device` 且 `ensure_root` 成功 |
| QQ `login_required`(H08 掉线) | OneBot WS 重连成功且收到心跳 |

**可观测性**：
- 日志按天滚动**落盘**（Agent `run_agent.py`/`main.py` 加 `--logfile`；WinAgent 已有），`trace_id` 贯穿；`transition` 打结构化日志（旧→新 state/code/reason）。
- **错误信封 `reason` 契约**：管道层透传子进程错误码，不在中间层吞语义（`pipe.py` deadline 分支补 `reason:"wechat_read_catching_up"`；`_dispatch` 异常补 `log.exception`）。

## 3. 数据与接口

- 新增 `state_code = WECHAT_READ_FAILED`（登记 `02 §8.1/§3.9`；中文文案 `01 §2.10 codes.ts`）。
- 告警码：新增「读取自愈耗尽/需人工重启」提醒码（具体码值实现时登记 `02 §3.7`）。
- 无新增 REST 端点；不改变既有 DTO 形状。

## 4. 界面对齐（01）

- `codes.ts`：`KEY_FAIL` 文案固定「微信取钥失败:消息读取与发送均不可用」；新增 `WECHAT_READ_FAILED` 文案「微信消息读取异常，暂停发送，自动重试中/需人工重启」。
- 账号详情：`WECHAT_READ_FAILED` 下不显示「重新取钥/重装」，显示「读取恢复中/重启」；`KEY_FAIL` 才显示取钥动作。

## 5. 失败、回滚与自愈

自愈动作一律受 `auto_recover` 与每小时上限约束；超限停止并告警（`AUTO_*_EXHAUSTED` 风格）。回滚：自愈动作本身幂等（重启进程/容器可重复），无数据回滚需求。

## 6. 安全与合规

- 不违反 D-2（不自动重登）、不 attach 主进程、不 frida、不 kill 其它工作负载；adb server 重启只影响我方 16000 与 qtrade 容器。
- 自愈不做「发消息」等有外发副作用的动作。

## 8b. 验收（动作 / 预期）

- 微信：构造「读超时」反例 → 退避重试 1:2:4:8:16、10 轮/600s 后停止并告警；`degraded` 下仍读、恢复自动回 `running`；`WECHAT_READ_FAILED` 与 `KEY_FAIL` 分码显示。
- 企点：构造「adb 僵死」→ H06 达阈值自动重启 server 并重连成功、不重拉容器；读库恢复。
