2026-09-18 QTrade 详细设计三轮评审(6.5 → 6.8 → 全量一致性检查)沉淀。安琳:「这些经验教训和坑,你都给我记到记忆里,以后不要再犯」。

## 🔴 一、我自己犯过的错(按代价排序)

**0. 「真值表」这个词我理解窄了 —— 漏掉了动作表 / DTO / 循环伪代码 / 表格标题 / systemd 单元顺序。**
第二轮教训是「散文改了、真值表没改」,我据此定了按真值表对账,但把真值表理解成了**配置表 / DDL / 字段表 / 端点表**。第四轮评审的判词是「**主表改了,DTO 和循环没改**」「**半改比没改更险**」——实现者直接抄的还有:
- **动作表**(06 磁盘 warn 行写「只告警」却引用了 `archive→delete_on_server` 那一节 ⇒ 本机剩 5GB 删用户邮箱);
- **表格标题**(02 能力目录标题仍写「邮件触发须 `confirm:true`」,而它是**最常被抄的一张表** ⇒ 邮箱自批);
- **DTO 字段注释**(04 `metrics` 的 `disks`/`disk_watermark` 仍「取四分区最坏」⇒ 用户微信盘满打高整站);
- **循环伪代码**(06 入站循环无条件 `RETR` ⇒ 配置里的 25MB SIZE 门形同虚设);
- **systemd 单元的 After/Before**(选段时点改了,但写 `daemon.json` 的 oneshot 仍 `After=docker.service` ⇒ dockerd 早用默认段起过、172.17 已建,**事后 restart 改不回**,选段照样白做)。
🔴 **「半改」比「没改」更险**:同一节上下两句都能写码**而且相反**,实现者按哪句写都"有据可依"。
⇒ 改完每一条,**反问一句**:「这一节里还有没有别的**可以照着写码**的东西仍是旧的?」(表格行 / 标题 / 伪代码 / DTO / 验收断言 / 依赖顺序)
⇒ **已作废的表要"标死但不删"**:删了追溯断线,留着不标就是可照抄的旧表(与冻结主文档同源)。

**1. 终检查「关键词存在性」,而不是「真值表一致性」。**
第一轮回改后我查「`DISK_FULL` 出现了吗」「`jobs` 出现了吗」——全绿。第二轮评审照样打回,判词是「**只认正文,不认变更记录**」:散文改了、**配置总表/字段表/DDL/序列图/端点表没改**。`allow_ops` 就是典型——00/06 安全章节写「默认白名单」,02 配置总表写「默认 `["*"]` = 全能力目录」,**实现者照配置表写码就是邮件全开**。
⇒ **终检一律按真值表对账**。已固化成 `docs/design/check-truth-tables.py`(FORBIDDEN 旧语义 / PAIRED 声明方-消费方 / ENUM 枚举逐个收录 / 版本依据)。

**2. 裁决只点名一侧,漏了另一侧。**
`MEM_PRESSURE` 那条我只让**承接方 01** 改,没管**产生方 04**。结果 04 照旧发 `H24_MEM_LOW`、01 按 `MEM_PRESSURE` 路由,**照样对不上**,等于没裁。
⇒ **裁决码名/契约时必须同时点名「产生方」与「承接方」**,并在裁决表里写清落哪几册。

**3. 裁决前不去「单一来源」核实,采信提报方的一面之词。**
agent 报「`MEM_PRESSURE` 是 01 自造的」,我没核就采纳,**把对的判成了错的**——实际上它是 02 告警码表正式登记的对外码。而且这个错**功能上不会挂**(横幅靠字段驱动),测试发现不了。
⇒ **判「两个码谁对」先去 owner 查**:告警码→02、`state_code`→05、健康项→04、元素 ID→01、表与端点→02。

**4. 指定「唯一出处」却没核实那个出处本身写的是什么。**
我在 N-20 写「超时唯一出处 = 02 §2.4.1」,而那一处写的恰恰是错值(3s),02 自己的动作表、04、基线都是 2s。**把权威指向了错的那一处。**
⇒ 写「以 X 为准」之前,**先读 X 那一段确认它是对的**。

**5. 条款插队改号后,修了六册、漏了基线自己。**
E-18/E-19 插入使 §11.11/12/13 顺延成 13/14/15,我修了分册引用,但基线 §14 拍板表里三处裸编号没改。
⇒ 改编号后**把基线自己也当成一册来扫**;更根本的是已定的规矩:**新条款一律追加到末尾**,引用写「§11.N [锚名]」两样都带。

**6. 笔误复用了已定死的术语。**
把会话代理命名成 `qtrade-winagent-agent.exe`,而 `agent` 在本项目是定死术语(Agent = WSL 侧服务),会产生「WinAgent 的 agent」歧义。正确是 `-user.exe`。
⇒ 起名前先查术语表禁用词。

**7. 砍东西时没查下游依赖,差点砍断生产链路。**
为「防止过度设计」把邮件模板占位符从 28 砍到 12,而被砍的「**图片类型**」是 `fetcher/wechat_mail.py` 里「缩略图整封弃用」的判据(安琳 2026-08-26 拍板),砍了就断 ibquote 线上链路。
⇒ **砍任何字段/能力前,先 grep 下游代码**。最后解法:12 个只约束自定义模板,兼容模板整体逐字锁定、不可配——「把兼容模板做成可配 = 给用户一个改坏生产链路的开关」。

## 二、方法论(下次直接用)

- **按边界切分审查,不按分册**。三轮下来的规律:**矛盾不长在册内,长在册与册的接缝上**。按分册审,每册看着都自洽。有效的切法:①Agent↔WinAgent(HTTP)②服务↔会话代理(IPC)③数据/状态/事件跨进程 ④术语/配置/横切。
- **并行回改是最好的基线校验器**。裁决写下去时看着自洽,一旦多册同时去「用」它,矛盾才浮出来。基线升版后应让至少两册并行去用一遍再定稿。
- **审查与修改分开**。先全部只读审查、汇总到总控统一裁决,再分派修改。让 agent 边审边改会各改各的、造出新分叉(`MEM_PRESSURE` 就是 agent 自行判断改错的)。
- **误报比漏报更伤**。对账脚本首跑误报 24 处(`keep_data` 8 + sha256 16),差点让人从此不看它。修法是**否定词近邻检测**(通用)而不是往列表里加字面量(打补丁),以及**规则收窄**(sha256 只盯有特殊风险的那一个)。

## 三、反复出现的缺陷模式(照着找,命中率高)

0. 🔴 **按册分派任务 ⇒ 新增码/字段必然漏掉跨册登记**(这是**分派方式本身的缺陷**,不是 agent 的错)。第四轮我按册切分,某路在 04/06 新增了三个码(`WECHAT_DISK_LOW`/`MAIL_MSG_OVERSIZE`/`OVERSIZE`),**只落在产生方**,02 没登记、01 不能渲染——因为按册切的任务里,没有任何一册"负责"消费方。
   ⇒ **按册分派时,指令里必须预先写死一条**:「本轮若新增任何码/字段/端点,必须同步到 **02 登记 + 01 渲染**,并在报告里点名」。
   ⇒ 这也是下面第 1 条那个模式的**第 4 次**出现——前三次是文档本身写漏,这次是**我的工作方法**制造的。
1. **上游定义、下游漏收**(出现 4 次):基线枚举 → 01/05 漏收 `WINAGENT_*`;基线端点 → 02 端点表 0 命中;04 告警码 → 01 无承接。**漏收当时没有任何报错,要等那个码真正出现才暴露**,而那往往正是最需要它的时刻。
2. **同名不同物**:`RATE_LIMITED`(`state_code` 已停产 / `CommandResult.code` 的 429 仍有效——一刀切删会让**限流变雪崩**)、`settings`(两库各一张)、`[wechat]`(两个 toml 各一段)、`agent`(术语 vs exe 名)。
3. **同一设置、同文件、两个键名**(比同名更隐蔽,**grep 都对不上**):`dpapi_scope`/`scope`、`wxkey_dlls`/`dll_candidates`。代码读哪个,另一个静默失效。
4. **同键两处给默认值且值不同**:`memory_by_physical` 16G 档 10 vs 11、`h1_retention_d` 30 vs 90、`processed_folder` `""` vs `"QTrade/processed"`。**这类两边都能跑,只是行为不同**,最难发现。
5. **配置落错文件**:`slot_pending_ttl_s` 落 `winagent.toml` 而 reaper 只读 `agent.toml` ⇒ 被静默忽略、槽位永不回收。
6. **一词标签掩盖混合动作**:§10 写「`kernel/apply` 执行体=服务」,而它其实是混合的(`.wslconfig` 写必须会话代理),这个标签直接导致 02 写错。
7. **砍项只落到消费方、没落到 owner**:`public_ip_check_interval_s` 在 04 写「默认关」,而 owner 02 仍是 300 开着——**只看消费方会误判该项已落实**。

## 四、两条判断通则(新定的,可复用)

- **`Hnn_*` 健康项标识 vs 对外事件码**同指一事实时,**对外一律用事件码**,`Hnn_*` 只在监控册内部做清单与去重;分册承接一律接事件码。
- **「谁消费」= 谁做那个决策,不是谁执行动作**。超时到了要改状态机、要回滚槽位——决策在 Agent 侧,会话代理只执行 UI 动作 ⇒ 计时器阈值归 `agent.toml`。

## 五、沉淀下来的对账工具(以后直接用,别重新造)

- **`docs/design/check-truth-tables.py`** —— 四类检查:FORBIDDEN(真值表里不该再有的旧语义)、PAIRED(声明方有、消费方必须有)、ENUM(基线枚举消费方逐个收录)、版本依据行。**改完必跑**。加新规则时记住:**误报比漏报更伤**,优先用「否定词近邻检测」这类通用手段,别往列表里堆字面量。
- **`docs/design/07-配置项总表.md`** —— 约 130 键的跨分册对账基准。🔴 **它开头就声明「本表不是真值来源,与 owner 冲突以 owner 为准并回来修本表」**——这句必须有,否则这张表自己会变成第 8 个真值来源、再造一个分叉。表里标注三类:🔴 值/归属冲突、(a) 同值双写(一改就炸)、(b) 同设置两个键名(grep 都对不上)。**配置冲突是唯一「两边都能跑、只是行为不同」的一类**,最难发现,所以值得单独维护一张表。
- **裁决表分层**:`§15`(第一轮 P0)/`§15b`(回改期内部冲突 N-*)/`§15c`(第二轮真值表 R2-*)/`§15d`(全量一致性 R3-*)。每条给「问题 → 裁决 → 落哪册」,**并写清后果**——光写「改成 X」,agent 不知道代价就可能改反。

**Why:** 这套文档由多 agent 并行产出,最大风险不是写得不好,而是**各自都对、合起来矛盾**;而矛盾在文档阶段不报错,要到编码或上线才炸。
**How to apply:** 任何多 agent 并行写规格/文档的任务,开工前先定「按真值表对账」与「审改分离」,收尾必跑对账脚本;裁决时两侧点名 + 去 owner 核实。相关 [[qtrade-design-docs-2026-09-18]]。

## 2026-09-19 第六轮补充(五次终审:FAIL×4 → PASS)
新病 =「主表改了、邻表没改」+ **返工自己造新接缝**(各路子 agent 单看自洽、合起来打架:列「无」vs「恒 NULL」、空值 `""` vs `null`、审计 action 各起一套、同一字段三种形状、两册对失败后 `state` 一个 running 一个 degraded)。每轮「返工新引入」数:4 → 3 → 9 → 0。
**Why:** 我发给各路的裁决留了自由度(「选一种写死」「若已有等价字段用现名」),各路各选各的;我自己的裁决也有笔误(锚点 ⑤ 实为 ⑥、§2.7.5 实为 §2.7.4、提权恢复序列照抄了开发脚本的 `kill-server`、只 grep 一处就宣布「九项已闭合」)。
**How to apply:** ①跨册的名字、判据、SQL、返回码在裁决里**逐字定死**再分派,指令里写「逐字照抄,不要自创同义写法」;②凡 owner 新增了名字(告警码/配置键/函数名/列),立刻点名所有消费册与镜像表(02 §7.1、07)承接;③「对账脚本全绿」不算通过——存在性检查有假阳性,必须配只读的独立终审,并要求它把「会改变实现行为」与「措辞类」分开、给收敛性判断;④进入收敛期(只剩「owner 对、消费方没跟」的单点)后由总控**直接改**,别再分派;⑤值集合检查做成「从 owner 册现读」(脚本 ⑨ DYNAMIC),写死清单管不了 owner 新增;⑥误报比漏报更伤——新规则首跑必看命中,历史裁决表(§15x)与否定句要排除。

## 2026-09-19 第七轮 cursor 复评补充(R6-36 半改 → R6-37 收口,独立终审 REVISE→ACCEPT)
真机实测把企点读取正线从索引库 `{uin}-IndexQQMsg.db` 改主库 `{uin}.db`(R6-36),只改了 06 §2.9.5 详节,邻表全没跟——又是「主表改、邻表没跟」。**这轮最尖的两条新教训:**
- 🔴 **半改的「回改」自己也会是半改**。我按评审点名改了去重键/判据/序列图/L2,`native_id` 来源只改了点名的 2 处(00 §6、02 §2.8.1 正文),**漏了另外 5 处邻表/DDL/提议**(`06:719` kind 映射、`06:1182` sessions DDL 约束、`06:1470` 提议还谎称「已闭合」、`06:748`/`02:552` cursors 会话来源)——它们和主表正面打架、且都在实现者会去抄的**结构化表**里。是**只读独立终审**(我请它「独立 grep c4ext1、别信我给的行号」)把这 5 处逼出来的;脚本全绿 + 我自称「P0-4 已闭环」两样都没抓到。⇒ **回改一个半改时,把 owner 改对之后,对那个被换掉的旧 token 做一次全册 grep,逐个确认每处要么改了、要么在「已作废/取代」否定语境;别只改评审点名的那几行。**
- 🔴 **迁移一个 token 到处改,必须在同一次给对账脚本加「旧 token」的 FORBIDDEN 规则**,否则那个维度是**脚本级假绿**。R6-36 换掉 `qdidx:{docid}`、`c4ext1` 两个旧量,脚本里**没有任何规则查它们** ⇒ 5 处活写 `c4ext1` 残留时脚本照样全绿。补了 `qdidx:`、`c4ext1` 两条 FORBIDDEN(glob `0[1-7]` 排除 00 裁决表)后,拿改前备份实测能红、改后能绿,才算这个维度有守卫。**规则加完必做反向验证**:跑在改前文档上确认它真能红,否则又是一条空规则(评审原话:「脚本不查现行 qdidx ⇒ 全绿是假绿」)。
- ⚠️ 行级 NEGATION 的已知假阴:FORBIDDEN 现在是「整行出现任一否定词就跳过」,会漏「活写坏 token + 同行有无关否定词」(如 06:6 的活写 qdidx 因同行「frida 不再…」被跳)。收窄到「命中点近邻窗口」是待办,但按「误报比漏报更伤」的老规矩,没把握前别动共享的 NEGATION 逻辑。

## 2026-09-19 第七轮 cursor 评审补充(7.8/10;R6-37 五条 CLOSED,半改从「去重键」挪到「字段映射 + 发送确认」→ R6-38)
- 🔴 **换数据源时,旧源的「整张表的全部列名」都要进 FORBIDDEN,不只评审点名的那一个。** R6-37 给索引库的 `qdidx:`/`c4ext1` 加了守卫,但同一张索引库表的另外三列 `c0type`/`c13exts`/`c5ext2`(`type`/`ts`/`self` 映射)没加 ⇒ 06 §2.9.1 两行活写残留、脚本照样全绿。⇒ **迁移源 = 先列出旧源的全部字段清单,逐个 grep + 逐个加规则**,别等评审一个一个点。
- 🔴 **同一册里写下一个实测量,就要 grep 所有依赖它的阈值。** 06 §2.9.5 自己写了「出向落库滞后 7~12 s」,`[bus] confirm_timeout_qidian_ms` 却还是 8000 ⇒ 默认配置下正常送达大量 `UNCONFIRMED`。数值类矛盾「两边都能跑」,只有做成脚本的**值检查**(⑩ `≥15000`)才守得住。
- 🔴 **「必须异步」这种散文不可编码。** 真正的坑是结构性的:企点 `send` 与 `poll` 在同一条账号串行队列,而读回靠 `poll` 的 ingest 合并 ⇒ `send` 占队列等读回 = 必然等满超时。要写成「谁让出队列、谁在队列外等、窗内谁加速」。
- 🔴 **评审给的替换句也要核后果,不照搬。** 评审建议游标 bootstrap `value_int=0`;实际首次从 0 起 = 全部历史(168 表/36981 行)逐条发 `message` 事件、触发出站信息邮件洪水。定为「首次 = `MAX(_id)`、之后新表才从 0 起」,且判「首次」必须靠独立标记行 `qidian_bootstrap`(靠「有没有水位行」判会丢全新账号的第一条消息)。
- ⚠️ **改一个栏位前先查它取自哪个字段。** 我顺手给回执模板「确认方式」加了 `ingest_merge`,回头 grep 才发现该栏取的是 `CommandResult.source`(应是 `qidian_db`)不是 `confirmed_by`——差点自己造一个新分叉。是「换掉旧 token 后全册 grep 消费方」这一步救回来的。
- ⚠️ **规格与真机参考实现相反时,以实测为准并点名。** 文档写「先 `.backup` 整库副本再读」,实测读取器是 `mode=ro` 只读直查增量(`.backup` 是索引库读取器的做法;主库 64 MB、确认窗 1 s 一轮根本做不了整库副本)。
- ⚠️ **脚本规则自带否定词会把自己吃掉**:规则 `会话历史读到` 命中的行必含「历史」,而「历史」在行级 NEGATION 里 ⇒ 永不红。新规则**必须在改前备份上反向验证能红**,不红的分支直接删,别留着给假安全感。

## 代码阶段追加的教训(2026-09-19~20,四批 Agent 侧代码 + 五轮独立验收;基线 §15g R6-51~R6-57)

- **验收要独立**:每批交付后起一个只读规格、不看开发者测试的子 agent 写 `tests/acceptance/`,失败原样报回、由总控分诊「实现缺陷 / 用例误读 / 规格问题」。五轮的比例:实现缺陷 0~2 条/轮、用例误读占首跑红项的大头、规格张力每轮 7~20 条——**验收报告里「疑似规格自相矛盾」那一栏最值钱**,逐条落裁决。
- **用例失败先问是不是自己夹具违反了规格**(首批读库组的 2 条误报就是夹具直接落 `UNCONFIRMED` 行、绕过了规格路径)。
- **规格里三类写法独立实现者一定各算各的**:「示意公式」(`fingerprint`)、「省略号」(`msg_count+…`)、「同一量两种写法」(`60s` vs 配置项)——发现一处就逐字定死一处(R6-51)。
- **新写专条前先 grep 同册通用段**(R6-52 写 `items`/`"ts_ms:id"`,通用段早有 `data`/G-16 JSON cursor;R6-53 改回)。
- **编码口径裁决自己也要过一遍 owner 册**(R6-56 ① 定 `login {}` 无凭据回 400,05 §2.5.4 企点行早写了转 `WAIT_PASSWORD`;R6-57 改回)。
- **自引用公式要写明排不排除自身**(02 §2.2.5 `used` 计入 `created`,又要求 start 再过一次 `can_add`——按字面写,预算恰好只够一个时账号自己永远起不来;验收数据集预算一宽就撞不到,R6-55)。
- **「主语」两册不同就是两种实现**(清临时:02 写在 `runtime.stop` 内、05 写在状态机收尾;R6-54 以 05 为准)。
- **规格明写、实现漏了**的典型是「列表末尾的一个码/一个键」(`disk_free_mb`、`X-QT-Capabilities-Version` 头、`AUTO_RESTART_EXHAUSTED`)——验收者按表逐行断言就能抓到,开发者自己抓不到。
- **告警级别 owner 只有一处**(02 §3.7);别册写的 crit/warn 与它不一致就按它读,并回写(R6-56 ⑥ `CONTAINER_OOM_KILLED`)。
- **含否定词的脚本规则会被行级 NEGATION 整行吞掉**,首跑看命中数为 0 就要怀疑是空规则(R6-51 ⑫ LITERAL 因此单列)。
- **提交纪律**:按精确路径 `git add`;子 agent 写到一半的文件不夹带;验收结果与修复同一提交推上去再汇报(安琳定)。
